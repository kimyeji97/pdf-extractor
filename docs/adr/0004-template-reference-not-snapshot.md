# 0004. 템플릿을 스냅샷이 아닌 참조 조합으로 정의

## Status

<!-- proposed · accepted · deprecated · superseded -->
accepted

---

## Context and Problem Statement

REQ-30에서 표지·각주·워터마크를 묶은 "템플릿" 엔티티를 도입한다. 세 자산은 REQ-29까지
각각 독립 CRUD(`cover.py`·`footnote.py`·`watermark.py`)로 이미 존재하고, 문제집 생성은
`extract-v2`가 `cover_id`·`footnote_id`·`watermark_id`를 받아 처리한다.

템플릿이 이 셋을 **어떻게 담을 것인가**가 데이터 모델의 갈림길이다 — 자산의 id만 가리키는
**참조**인가, 값(텍스트·이미지 바이트)을 복사해 보관하는 **스냅샷**인가.

이 선택은 한 번 정하면 되돌리기 비싸다. 스냅샷으로 시작한 뒤 참조로 바꾸면 복사본을 원본에
다시 이어 붙일 방법이 없고(어느 표지에서 복사됐는지 기록이 없다), 참조로 시작한 뒤 스냅샷으로
바꾸면 기존 템플릿의 "그 시점 값"을 복원할 수 없다.

**논의 과정에서 전제 하나가 잘못 깔려 있었다** — "참조로 하면 템플릿을 수정했을 때 이미 생성한
문제집도 바뀐다"는 우려. 실제로는 **어느 안에서도 바뀌지 않는다.** 생성 결과는
`results/{export_job_id}/result.pdf`로 구워진 정적 파일이고(`pdf_service` Step 5 →
`upload_file`), 표지·각주·워터마크는 생성 순간 PDF 안에 픽셀·텍스트로 박힌 뒤 어떤 id도
참조하지 않는다. 문제집 메타(`workbooks/{id}.json`)도 당시 `cover_id`조차 들고 있지 않았다.

즉 **"과거 산출물 보호"는 이 결정의 판단 근거가 될 수 없다.** 그 전제를 걷어내고 나서야
실제 트레이드오프가 드러났다.

---

## Decision Drivers

- TODO 신규 항목 ④ 원문의 표현 — *"등록된 걸 조합해서 개인만의 템플릿으로"*
- 표지·워터마크는 **이미지**다(각 최대 10MB, JPEG/PNG). 복제 비용이 텍스트와 다르다
- 참조를 택하면 **dangling(끊어진 참조)** 을 반드시 다뤄야 한다 — 현재 코드는 dangling id를
  `if meta:`로 조용히 건너뛰어 **에러 없이 표지가 빠진 PDF**를 낸다
- 자산 3종이 이미 독립 엔티티로 서 있고, 각각 자기 CRUD·스토리지·목록 화면을 갖는다

---

## Considered Options

1. **참조** — 템플릿은 `{template_id, name, cover_id, footnote_id, watermark_id}`
2. **스냅샷** — 템플릿이 각주 텍스트와 표지·워터마크 이미지 바이트의 사본을 소유
3. **참조 + 생성 시점 스냅샷** — 템플릿은 참조, `WorkbookMeta`에 생성 당시 값을 별도 기록

---

## Decision Outcome

**선택: 1. 참조.**

템플릿은 자산의 id 세 개와 이름만 들고, 실제 값은 생성 요청 시점에
`start_extract_v2`가 해석(resolve)한다. 자산을 고치면 그 템플릿으로 **앞으로 만들** 문제집에
반영되고, 이미 만든 PDF는 그대로다.

dangling은 이 결정에 딸린 비용이므로 두 겹으로 닫는다 — 자산 삭제 시 참조 검사 후 차단
(사용자가 명시적으로 강제 삭제를 고를 수 있다), 생성 요청 시점에 참조 검증 후 400.
상세는 [PLAN-30](../plans/PLAN-30-template-entity.md) `## 결정`.

**Rationale:**

- TODO 원문이 *"등록된 걸 조합"*이고, 자산 3종이 이미 독립 엔티티라 참조가 그 그림에 맞는다.
- 표지를 개선하면 그것을 쓰는 모든 템플릿에 한 번에 반영된다. 스냅샷이면 템플릿마다 다시
  만들어야 하고, 템플릿이 늘어날수록 그 비용이 선형으로 커진다.
- 이미지 사본이 생기지 않는다. 템플릿 5개가 같은 표지를 쓰면 스냅샷은 사본 5개다.
- 스냅샷이 얻는 실익은 **dangling 회피 하나**인데, 그건 삭제·생성 양쪽의 참조 검증으로 따로
  닫을 수 있고 그 검증은 어차피 직접 id 경로(구 프론트 호환) 때문에 **참조 여부와 무관하게
  필요하다.**

---

## 기각한 안

### 2. 스냅샷

**기각 이유** — 얻는 것이 dangling 회피 하나뿐인데, 그 하나는 별도 검증으로 닫을 수 있다.
반면 치르는 값은 이미지 사본(각 최대 10MB × 템플릿 수)과 "표지를 고쳐도 템플릿에 반영되지
않는다"는 영구적 마찰이다. 처음에 스냅샷을 지지하던 근거("이미 만든 문제집이 바뀐다")는
사실이 아니었다 — 위 Context 참조.

**재검토 조건** — 다음 중 하나가 참이 되면 다시 볼 만하다.

- 템플릿이 **다른 사용자와 공유**되기 시작할 때(REQ-28). 남의 표지를 참조하는 템플릿은
  그 사람이 표지를 지우면 깨지고, 삭제 차단이 남의 자산에까지 미치는 건 받아들이기 어렵다.
- 자산에 **버전 개념**이 생길 때. "그때의 표지"를 가리킬 수단이 있으면 스냅샷의 이점을
  복제 없이 얻는다.
- 템플릿 수가 자산 수를 크게 넘어서서, 삭제 차단이 실질적으로 "자산을 못 지우는" 상태가 될 때.

### 3. 참조 + 생성 시점 스냅샷

**기각 이유** — 논의 중 제3안으로 올렸으나, **dangling 문제를 전혀 줄이지 못한다.**
템플릿 → 자산 고리는 여전히 끊어질 수 있어 삭제·생성 검증이 그대로 필요하다. 순수한 추가
작업이고, `WorkbookMeta`에 남길 값을 id로 하면 안의 절반(`template_id` 저장)은 REQ-30 범위에
이미 들어와 있다.

**재검토 조건** — 결과 화면에서 "이 문제집이 어떤 표지·각주·워터마크로 만들어졌는지"를
**자산이 삭제된 뒤에도** 보여줘야 한다는 요구가 생기면. 그때는 id가 아니라 값(이름·썸네일)을
`WorkbookMeta`에 남겨야 한다.

## Consequences

**Good:**

- 자산을 고치면 그것을 쓰는 모든 템플릿에 한 번에 반영된다
- 이미지 중복 저장이 없다 — 스토리지도, 업로드 경로도 그대로
- 템플릿 레코드가 작아 `templates/{id}.json` 하나로 끝난다(표지처럼 이미지 짝이 없다)

**Bad:**

- **dangling을 영구히 다뤄야 한다.** 자산 삭제에 참조 검사가 붙고(409 + 강제 삭제),
  생성 요청에 참조 검증이 붙는다(400). 둘 다 없으면 "조용히 빠진 PDF"로 되돌아간다
- 표지를 교체하려면 새로 올리고 → 템플릿을 고치고 → 옛것을 삭제하는 3단계다
- 자산 삭제 경로가 템플릿 전수 스캔을 하게 된다(개수가 적어 비용은 무시 가능하나, 스토리지
  백엔드 양쪽에 목록 조회가 생긴다)
