## 1. 목표와 측정 조건

**목표** (2026-10-01 사용자 결정)
- 분석 중이든 아니든 **모든 API 1s 미만**
- 예외: 파일 업로드 · SSE 알림 스트림(`/api/notifications/stream`)
- PDF·이미지 내려받기: 1s 미만이 목표, 해결 방안이 안 보이면 3s까지 허용, 그래도 안 되면 예외

**기준 사용량** (오픈 후 내려갈 수 있음): 사용자 10명 × (분석 5건 + 생성 5건) / 일 → 하루 분석 50 · 생성 50

| 시나리오 | 부하 |
|---|---|
| 평시 | 분석 없음 |
| 피크 ① | 한 사용자 5건 연속 업로드 — 분석 5건 동시(B17 한도) |
| 피크 ② | 10명이 동시에 한 건씩 — 분석 10건(실행 5 + 대기 5) + 생성 3건 겹침 |

**방법**
- 계정 둘: 측정 계정 `p06-loadtest@example.com`(일반 사용자, dev 가입) · admin(전체 데이터 집계)
- GET API 36종(목록·현황판·상세·문항·썸네일·각주·워터마크·표지·템플릿·알림·상태 등)을 시나리오 동안 반복 측정
- 경로 둘을 함께 잼: **터널 경유**(실제 사용자 경로) · **앱 직접**(태스크 공인 IP:8000, 터널 우회 — 원인 분리용)
- CPU·메모리는 CloudWatch `AWS/ECS` 서비스 지표(1분 최대)
- 사양 비교: rev 4를 복제해 cpu/memory만 바꾼 측정용 리비전(rev 5 = 1 vCPU/2GB, rev 6 = 2 vCPU/4GB)으로 같은 시나리오 반복 → 측정 후 deregister, rev 4·`desired 0` 복귀

## 3. 원인

| # | 원인 | 근거 | 사양 상향으로 |
|---|---|---|---|
| ① | **Cloudflare Tunnel 지연** | 같은 시각 빈 `/health`: 앱 직접 0.01s / 터널 중앙값 0.43s·최대 14s / 같은 Cloudflare의 정적 Worker 0.18s. CPU 5~12%로 한가할 때도 튐. 서버 로그 시각 ≈ 클라이언트 수신 시각(차 0.02s) → 지연은 **요청이 앱에 닿기 전**. 동시 업로드 중 앱은 200인데 클라이언트는 **520**(1건) | **해결 안 됨** |
| ② | **데이터 양에 비례하는 API** | 평시에도 `stats_detail` 미탐지 3.2s · 오탐 1.5s. job 0건 계정도 같음 → 전체를 훑고 소유자로 거르는 구조(추정, 코드 미확인) | **해결 안 됨** (데이터가 늘면 악화) |
| ③ | **분석의 CPU 점유** | 분석 5건 동안 CPU 100% 6분, 앱 응답 중앙값 2.6배. 2 vCPU에서 포화 해소(최대 58%) | 해결 (2 vCPU) |
| ④ | **메모리** | 분석 동시 한도(5, B17)는 있지만 생성 프로세스(`ProcessPoolExecutor` 2)의 메모리가 그 위에 얹혀 1GB 초과 | 해결 (2GB 이상) |

터널 지연이 QUIC 때문인지는 **추정**이다(cloudflared 기본 프로토콜 QUIC, 로그에 오류 없음). 프로토콜을 HTTP/2로 바꿔 비교해야 확정된다.

## 4. API별 현황 (2 vCPU / 4GB, 앱 직접, 평시 중앙값)

| 구분 | API |
|---|---|
| **1s 초과** | `stats_detail` 미탐지 6.4s · 오탐 4.5s · `stats` 1.45s · `stats_detail` 수동 1.42s |
| **1s 근접** (0.9~0.97s) | `jobs`(SOURCE·EXPORT 목록) · 알림 목록 · 템플릿 · `stats_detail` 처리 중·대기 |
| **목표 안** (0.3~0.6s) | job 상세 · 페이지 목록 · 문항(전체·쪽별) · 페이지/문항 썸네일 · 각주 · 워터마크 · 표지(목록·이미지) · 문제집 · 상태 |

목표 안 그룹도 터널 경유로는 수 초씩 튄다 — ①을 풀어야 목표에 들어온다.

## 5. 운영 환경 권고

- **사양**: 최소 **1 vCPU / 2GB**(죽지 않음, 단 분석 중 CPU 포화) · 권장 **2 vCPU / 4GB**(CPU 여유)
- **현재 dev(0.5 vCPU / 1GB)는 운영에 그대로 쓸 수 없다** — 기준 사용량 피크에서 OOM
- 비용 참고: dev 0.5 vCPU / 1GB 상시 가동 시 월 ~$23. Fargate 요금은 vCPU·메모리에 비례 — 2 vCPU / 4GB는 약 4배(추정)
- 분석 동시 한도·사양을 다시 정할 때는 **생성 프로세스 메모리를 합산**할 것(④)
- 목표 달성에는 사양 외에 **현황판 계열 API 개선(코드)** 과 **터널 개선(인프라)** 이 함께 필요하다 — REQ-P06 Phase 3에서 결정

## 6. 다시 잴 때

- **터널 vs 앱 분리**: 서버 로그에 요청 시작 시각이 없어 로그만으로는 못 가른다. 태스크 공인 IP로 직접 붙어 잰다 —
  보안 그룹 `sg-07d2336bbf0ec09ea`에 측정자 IP만 8000번을 잠시 열고(자동 모드 분류기가 막으면 사용자가 직접 실행) 끝나면 revoke. 태스크가 바뀌면 공인 IP도 바뀐다
- **사양 비교는 같은 데이터 양에서** — 이번엔 사양 순서대로 재며 측정 job이 사양마다 약 15건씩 쌓였다. 그래서 ② 데이터 비례 API의 사양별 수치(3.2→5.7→6.4s)는 사양 효과가 아니다
- 측정용 태스크 정의 리비전은 **반드시 deregister** — 콘솔 "서비스 업데이트"가 최신 활성 리비전을 기본으로 고른다(2026-09-28 프로브 rev 3 사고)
- Cloudflare는 기본 UA를 403으로 막을 수 있다 — 브라우저 UA를 붙인다(P05)
- 측정 데이터: dev에 측정 계정 소유 SOURCE 약 35건 · 생성 약 9건이 남아 있다(2026-10-01 기준, 정리 미정) — 현황판 계열 API를 느리게 만드는 요인
