# PLAN-B10 · 문제집 생성 중 화면 이탈 시 메타·다운로드 유실

> 출처: 2026-07-30 세션 (REQ-F09 계획 점검 중 파생) · 작성: 2026-07-30
> 상태: 📝 **확정 — 미결 0건, 착수 대기** (구현 시작 시 🟡)

## 배경

문제집 생성을 걸어 둔 뒤 편집 화면을 떠나면 **PDF는 서버에 만들어지지만 생성 이력에는 영원히
나타나지 않는다.** 사용자 입장에서는 "생성이 실패했다"로 보이고, 실제로는 결과물이
`results/{job_id}/`에 남아 아무도 참조하지 않는 고아가 된다.

원인은 문제집 메타를 만드는 유일한 주체가 **프론트 폴링의 `DONE` 분기**라는 것이다
(`extract.py`에 `workbook` 언급 0건 — 백엔드는 메타를 만들지 않는다). 그 폴링은
언마운트에서 `clearInterval`로 죽으므로, 화면을 떠나면 `createWorkbookMeta()`가 영원히
호출되지 않는다. 자동 다운로드(`a.click()`)도 같은 분기 안에 있어 함께 사라진다.

**생성 이력 화면은 `workbooks/`만 읽는다** — 메타가 없으면 결과 PDF가 존재해도 목록에 없다.

> 이 버그는 REQ-F09(완료 알림) 계획을 점검하다 코드 흐름으로 발견했다. F09가 폴링을 앱 셸로
> 올리면 자연히 함께 고쳐지지만, **불편(알림 없음)과 데이터 손실은 급이 다르므로 분리해
> 먼저 고친다**(2026-07-30 사용자 결정).

## 범위

**포함**

- 생성 중 화면 이탈·새로고침·탭 종료 시에도 문제집 메타가 남게 한다
- 위 상황에서 유실되는 자동 다운로드 처리
- `createWorkbookMeta` 실패를 침묵으로 삼키는 `catch {}` (editor/index.jsx) 정리

**제외**

- **알림 표면(벨·스낵바·브라우저 알림) 일체** — REQ-F09 소관. B10은 "결과가 남는가"만 책임진다
- **전역 폴링 인프라 신설** — F09가 만든다. B10이 그걸 기다리면 "먼저 고친다"는 결정이 무의미해지므로,
  B10은 F09 인프라에 의존하지 않는 해법이어야 한다
- **문항 감지(`boundaries_status`) 경로** — 이쪽은 결과가 job에 귀속돼 유실이 없다. 재감지 폴링이
  죽어도 다음 조회 때 상태가 보인다

## 결정

| 해법 방향 | **안 A′ — 백엔드가 생성 성공 시 메타를 쓴다** | 프론트 수명과 완전히 분리된다. 폴링이 죽든 탭이 닫히든 무관 | **안 B**(프론트 선저장) — 백엔드 무변경이지만 저장 호출 실패 창이 남고 갱신이 여전히 폴링 의존이라 `PROCESSING`에 멈춘 메타가 생긴다. **안 C**(이력이 export job 직접 조회) — 유실을 막지 않고 표시로 덮는 것이라 이름·선택 목록이 복구되지 않아 편집 복원이 안 된다 |
| 저장 시점 | **성공 시에만 쓴다** | 요청 시점에 `PROCESSING`으로 선저장하면 이력에 미완성·실패 항목이 노출되고 상태 필드·표시가 따라붙는다 | 요청 시점 선저장 |
| 자동 다운로드 | **편집 화면에 머문 경우로 한정** | 화면을 떠난 사용자에게 브라우저 다운로드를 강제할 수단이 없다. 이탈했으면 생성 이력에서 받아 간다 | 복귀 시 재시도 — 의도치 않은 시점에 다운로드가 시작되고 F09 알림과 역할이 겹친다 |
| 고아 복구 | **Phase 0에서 건수를 세고 판단** | 로컬에 `local_storage`가 없어 실데이터는 R2 dev에만 있다. 0건이면 복구 작업 자체가 불필요 | 무조건 복구 / 무조건 미복구 — 둘 다 건수를 모르고 정하는 것 |

> **안 A′가 예상보다 싸다.** `workbook.py` docstring은 프론트 주도 저장을 택한 이유를
> "extract-v2는 PDF만 생성하고 selections/layout 정보를 모르기 때문"이라 적어 뒀는데,
> **그 근거는 현재 사실이 아니다** — `ExtractV2Request`가 `selections`와 `layout`을 둘 다 받는다.
> 실제 격차는 3개뿐이다: 문제집 이름(`filename`/`name`, 같은 값이 들어간다), 선택 항목의
> `workbook_name`·`source_filename`. `title`은 이미 `label`로 같은 값이 넘어온다.
> **이 docstring은 수정 시 함께 고쳐야 한다** — 안 고치면 다음 사람이 같은 근거로 되돌린다.

## 작업 단계

- [ ] **Phase 0 — 재현 확정**

      완료 기준: 생성 시작 직후 다른 라우트로 이동 → `results/{job_id}/result.pdf` 존재 확인 +
      `workbooks/`에 대응 메타 없음 확인 + 생성 이력 목록에 미표시 확인. 3개가 모두 성립하면 확정.
      고아 데이터 건수도 이때 함께 센다(미결 2번 답).

- [ ] **Phase 1 — 스키마 확장**
      `ExtractV2Request`에 `workbook_name`, `SelectionItem`에 `workbook_name`·`source_filename` 추가.
      셋 다 `Optional` — 구버전 프론트 요청이 422로 깨지지 않아야 한다.
      완료 기준: 세 필드 없이 보낸 기존 형태의 요청이 그대로 200. 새 필드를 실은 요청도 200.

- [ ] **Phase 2 — 백엔드 저장 이관**
      `_process_extraction_v2`가 생성 성공 직후 `storage.save_workbook()`을 호출한다.
      `workbook.py`의 docstring(프론트 주도 저장 근거)도 함께 고친다.
      완료 기준: Phase 0의 재현 절차를 그대로 반복했을 때 **생성 이력에 문제집이 나타난다.**
      새로고침·탭 종료 경로에서도 같은 결과. 생성 **실패** 시에는 메타가 생기지 않는다.

- [ ] **Phase 3 — 프론트 정리**
      폴링 `DONE` 분기의 `createWorkbookMeta` 호출과 이를 감싼 `catch {}`를 제거한다.
      자동 다운로드는 남기되 화면에 머문 경우로 한정됨을 주석으로 명시한다.
      완료 기준: 편집 화면에 머문 경로에서 **문제집이 이력에 1건만 생긴다**(백엔드·프론트 이중 저장으로
      2건이 되지 않을 것). 자동 다운로드는 종전대로 동작.
      ⚠️ Phase 2 배포 **전에** 이걸 먼저 내보내면 저장 주체가 아무도 없는 구간이 생긴다 — 순서 고정.

- [ ] **Phase 4 — 고아 데이터 판단** *(Phase 0 실측 결과에 따름)*

## 제약·함정

- **`workbook_name`은 고유하지 않다**(계약 #17). 고아 복구나 중복 판정을 이름으로 하면 안 된다 —
  실데이터에 같은 이름 2건이 있다. 키는 `job_id`.
- **폴링의 `DONE` 분기에 부수효과를 두지 말 것** — 이 버그의 본질이다. 그 분기는 화면 수명에
  묶여 있어 "화면이 살아 있는 동안만 일어나는 일"만 넣어야 한다(UI 상태 전환). 영속 저장은 안 된다.
  → B10 완료 후 **`CLAUDE.md` 계약으로 승격 제안**(5절 참조).
- **`extract-v2`는 이미 배포된 API다.** 추가 필드는 전부 `Optional`이어야 하고, **백엔드를 먼저
  배포한 뒤 프론트를 내보낸다**(Phase 2 → 3). 순서가 뒤집히면 저장 주체가 없는 구간이 생긴다.
- **이중 저장 주의** — Phase 3에서 프론트 호출을 지우기 전까지는 백엔드·프론트가 둘 다 저장한다.
  `workbook_id`가 매번 새로 발급되므로 **같은 문제집이 이력에 2건** 뜬다. 검증 시 이 상태를
  버그로 오인하지 말 것(정상적인 과도기).
