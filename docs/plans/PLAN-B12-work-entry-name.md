# PLAN-B12 · 목록을 거치지 않는 작업 화면 진입 — 문서 이름이 job-id로 뜸 (+ 직접 진입 목록 복귀 재현)

> 출처: 2026-08-28 `docs/TODO.md` 신규 항목 ⑤ 원문 + 2026-09-03 D10 Phase 2 관찰(PROGRESS) + 2026-09-04 결정 3건 · 작성: 2026-09-04 · 상태: 📝 초안 (미결 1건 — Phase 2 재현 결과에 달림)

## 배경

**작업 화면(`/analysis/:jobId`)은 문서 이름을 진입 경로에 의존해 알아낸다.** `work.jsx`가 제목·브레드크럼에
쓰는 `filename`·`workbookName`을 `location.state`에서만 읽고, 없으면 `jobId`로 떨어진다. state를 넘기는
진입 경로는 **목록 카드 클릭 하나**뿐이다. 벨 알림 클릭(`navigate(/analysis/${job_id})`, state 없음)과
주소창 직접 입력·새로고침·뒤로가기는 state가 없어 **헤더 제목과 브레드크럼에 job-id가 그대로 보인다.**

요구 원문(2026-08-28 `docs/TODO.md` 신규 항목 ⑤):

> 벨 알림을 클릭하면, 분석으로 넘어가는데 문서 이름이 관리명이 아님. (job-id 인 듯)

원문의 추정("job-id 인 듯")은 맞다. 원인은 벨이 아니라 **작업 화면의 이름 출처가 한 경로에만 있는 것**이다 —
벨을 고쳐(state를 실어) 막으면 URL 직접 진입은 그대로 남는다.

**이미 답이 손에 있다.** F11 가드(`useAnalysisEntryGuard`)가 마운트 시 `GET /api/jobs/{id}`를 부르고, 그 응답
(`JobSummary`)에 `filename`·`workbook_name`이 들어 있다. 화면은 이 응답을 `jobInfo`로 이미 받아 원본 PDF URL을
꺼내 쓴다. 이름만 안 꺼내고 있었다.

**같은 무대에서 본 두 번째 증상** — D10 Phase 2(2026-09-03) playwright 자동화에서 "URL 직접 진입이 목록으로
돌아갔다. 카드 클릭 진입은 정상. 감지 상태는 DONE이라 F11 가드 대상은 아닌데 이유를 안 팠다"(PROGRESS). 한 번
관찰, 손으로 재현한 적 없음. **이름 버그와 원인이 다르다** — state 부재는 이름을 비울 뿐 이동을 일으키지 않는다.
번호 부여 시 "두 증상이 같은 원인인지는 착수 시 확인"으로 묶였고, 착수해 보니 **같은 원인이 아니다.**

## 범위

**포함**

- 작업 화면의 문서 이름 출처를 **`jobInfo`(가드 응답) 하나**로 — 벨·URL 직접 진입·새로고침·뒤로가기·목록 클릭
  어느 경로로 들어와도 같은 이름이 뜬다
- `jobInfo` 도착 전 헤더 제목·브레드크럼 마지막 항목은 **"불러오는 중…"** — job-id를 사용자에게 보이지 않는다
- 목록 카드 클릭의 `state: { filename, workbookName }` 전달 **제거** — 읽는 곳이 없어지므로 남기면 죽은 코드
- 두 번째 증상(직접 진입 → 목록 복귀) **재현 시도** — 재현되면 원인 확정 후 이 계획서를 갱신해 Phase 3으로,
  안 되면 관찰 기록만 남기고 종결

**제외**

- **벨이 알림에 이름을 실어 보내는 것**(`NotificationItem`에 `filename` 추가 등) — 이름 출처를 하나로 모으는
  결정과 반대 방향. 서버 스키마도 안 건드린다
- **가드의 조회 실패 시 이름** — 실패하면 가드가 진입을 막고 다이얼로그를 띄우므로(F11 "상태를 모르면 막는다")
  그 화면에서 이름이 보일 일이 없다. 별도 처리 없음
- **`getJobInfo` 호출 추가** — 가드가 유일 호출자다(F11 계획서 제약, 아래 제약·함정). 화면이 이름을 얻으려고
  한 번 더 부르면 같은 응답을 두 번 받는다
- **F12 현황판·D07 리디자인 잔여** — 별건
- **dev 프론트 배포** — 프론트 배포 정책(2026-08-28)상 로드맵 3단계 완료 시점에 모아서
- **증상 2의 가설 선제 수정**(가드 다이얼로그의 backdrop·Esc 닫기가 목록으로 보내는 것) — 재현 전에는
  원인이란 근거가 없다. 2026-09-04 결정: 재현 시도가 먼저

## 제약·함정

- **`getJobInfo`의 유일 호출자는 가드다**(F11 Phase 1 계획서 제약). raw `fetch`라 dedup이 없어 화면이 한 번 더
  부르면 같은 응답이 두 번 온다. 이름은 가드가 넘겨주는 `jobInfo`에서 꺼낸다 — 새 요청·새 훅을 만들지 않는다.
- **가드 응답이 실패하면 `jobInfo`는 `null`이고 화면은 차단 다이얼로그다.** 이름 코드가 `null`을 안전하게
  넘겨야 한다(옵셔널 체이닝). 실패 화면에 "불러오는 중…"이 남는 건 허용 — 다이얼로그가 덮는다.
- **`PageHeader`는 `title` 값을 `Typography`의 `title` 속성(툴팁)에도 넣는다.** "불러오는 중…"이 툴팁으로도
  잠깐 보이는데, 그건 의도된 값이라 문제없다. 단 job-id는 이 속성에도 나타나면 안 된다 — 단언은 `textContent`가
  아니라 **DOM 전체에서 job-id 문자열 검색**으로 잡는 편이 이 경로까지 덮는다.
- **작업 화면은 렌더 무대가 없다** — D11에서 `pages/analysis/work.jsx`는 API mock 5~6개가 필요해 소스 스캔으로
  대체했다. 이름 파생은 **순수 함수로 빼면**(예: `jobInfo`·`loading`·`jobId` → 표시 문자열) 단위 테스트가
  되고 화면은 그 함수를 부르기만 한다. D10의 `columnsForWidth`가 같은 이유로 `utils/`에 갔다. 네 경로 전부를
  렌더로 검증하는 건 이 범위에 비해 크다 — 벨 경로는 `NotificationBell` 테스트가 `navigate` 인자까지 이미 보고,
  화면 쪽은 "state를 안 읽는다"가 성립하면 경로 구분이 사라진다.
- **D11-07이 `work.jsx`를 소스 스캔한다**(`label: "분석"`). 브레드크럼 배열을 재구성할 때 그 문자열이 그대로
  남아야 한다 — 바뀌면 D11 회귀로 잡힌다.
- **가드의 판정은 마운트 시 1회**(F11 설계). 이름도 같은 응답이므로 화면에 머무는 동안 이름을 바꿔도(목록의
  이름 편집은 다른 화면) 갱신되지 않는다. 그게 맞다 — 편집은 목록에서 하고 작업 화면은 다시 들어온다.
- **증상 2 재현은 자동화가 아니라 실제 브라우저로** — 관찰이 playwright 무대에서 나왔고, cua-driver·playwright
  둘 다 입력 라우팅·타이밍 함정이 기록돼 있다(PROGRESS 2026-09-02·03). 도구 함정을 증상으로 오인하지 않으려면
  사람 손으로 먼저 본다. 재현되면 그때 콘솔·네트워크 탭을 연다.
- 브랜치: `main`에서 `feat/B12-work-entry-name` 생성 (`/implement` 게이트).
