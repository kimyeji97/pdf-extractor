## 배경

dev에서 PDF 여러 개를 연달아 "업로드 후 분석"하던 중 업로드가 `Failed to fetch`(Cloudflare 530 + CORS 에러)로
실패하기 시작했다. 530은 터널 뒤 오리진에 닿지 못했다는 뜻이고, CORS 에러는 그 530 응답에 CORS 헤더가 없어서
따라 나온 부수 증상이다.

- **실제 원인**: 2026-09-28 16:09:55 KST 백엔드 컨테이너 `OutOfMemoryError`(exit 137, 태스크 0.5 vCPU / 1GB).
  ECS가 새 태스크를 띄우는 ~1분 동안 모든 요청이 530.
- 직전 상황: `내신마스터(1~3회).pdf`(6.2MB · 212쪽 · 문항 820) 감지가 1분 40초째 도는 중에
  `심화대비.pdf` 감지가 끝나 썸네일 prewarm(스레드 12개)이 시작됐다.
- **로컬 실측 — 감지 하나가 이미 한도에 닿는다**: `내신마스터` 감지 단독 최대 RSS **1,032MB**
  (다른 3종 32쪽 안팎은 ~155MB). 메모리가 **쪽수에 비례**한다(~4.5MB/쪽).
- **누수 원인 실측**: pdfplumber는 읽은 페이지의 파싱 결과를 캐시에 쥐고 있는데, 감지 루프가 페이지를
  닫지 않는다. 측정 스크립트에서만 "다음 페이지로 넘어갈 때 이전 페이지 close"를 씌우면
  **1,032MB → 154MB, 시간 15s → 14s, 감지 결과(문항 820개의 page·번호·y·오탐 표시) 완전히 동일.**
  prewarm은 +50MB 수준이라 주범이 아니다.
- **부수 피해**: 태스크가 죽으면서 `내신마스터` job이 `boundaries_status=PROCESSING`으로 **영원히 멈췄다**
  (감지는 인메모리 백그라운드 작업이라 이어받거나 실패로 바꿔 줄 주체가 없다). 화면 "분석중 파일 수"에 계속 잡힌다.
- 동시에 도는 분석 수에 제한이 없다 — 업로드·재감지마다 백그라운드 작업이 하나씩 더 붙는다.

## 범위

**포함**
- 감지(`question_parser`)의 pdfplumber 페이지 누수 수정 — 다 읽은 페이지를 닫는다. 감지 결과는 바뀌면 안 된다
- 백그라운드 분석(감지 + 썸네일 prewarm)을 **동시 5개**로 제한하고, 초과분은 앞 작업이 끝날 때까지 대기
  (업로드 notify·direct 업로드·재감지 세 진입점 모두)
- 대기열에 들어간 job은 새 상태 **`QUEUED`**("대기 중"), 자리가 나면 `PROCESSING`
- 서버 시작 시 `QUEUED`·`PROCESSING`으로 남은 job을 `FAILED`로 전환하고 **실패 알림을 발행**
- 프론트: `QUEUED` 라벨·진입/재감지 규칙, 분석 목록 현황판에 **"대기 중" 타일 추가**
- 운영 환경 구성용 참고 수치 기록(아래 § 운영 환경 참고)

**제외**
- dev 태스크 CPU·메모리 증설 — 누수 수정 후 1GB에 동시 5개가 들어간다(아래 추산). 운영 환경은 구성 시 늘린다(사용자, 2026-09-28)
- 요청 경로 안의 동기 감지(썸네일·문항 조회의 캐시 미스 폴백, PDF 생성 `pdf_service`)의 동시성 제한 — 사용자 요청은
  "분석 동시 5개"였다. 누수 수정은 같은 함수라 이 경로들에도 자동으로 적용된다
- PDF 생성(`extract-v2`)의 메모리 — 실측하지 않았다
- 외부 큐(SQS 등) — 인프로세스 대기로 충분(단일 태스크)

## 운영 환경 참고 (prod 구성 시 읽을 것)

> 사용자: "cpu랑 메모리는 운영환경은 늘리면 돼" — 아래는 늘릴 때의 기준 수치다. 전부 **로컬(macOS) 실측**이고
> 컨테이너(Linux)에서 다시 재지 않았다. 규모 감으로만 쓸 것.

**메모리 (파일 1개 분석, 누수 수정 전 → 후)**

| 파일 | 쪽 · 문항 | 감지 최대 RSS 수정 전 | 수정 후(패치 실측) | prewarm 추가 |
|---|---|---|---|---|
| 내신마스터(1~3회) | 212쪽 · 820 | 1,032MB | 154MB | (측정 시 감지 peak에 가려짐) |
| 심화대비 | 33쪽 · 120 | 156MB | — | +51MB |
| 학교별 심화기출 Blue / Red | 32·31쪽 · ~100 | ~158MB | — | — |

- 프로세스 기본 ~90MB. 수정 후 파일 1개당 증분 ≈ 감지 ~70MB + prewarm ~50MB ≈ **120MB**
- **동시 5개 추산 ≈ 90 + 5×120 ≈ 700MB** → 1GB 안. 쪽수가 훨씬 큰 파일(수백 쪽 이상)이 섞이면 재측정할 것
- 운영에서 동시 수를 N으로 올리면 대략 `90 + N×120MB` + 여유 30%로 메모리를 잡는다

**CPU**
- 0.5 vCPU에서 5개가 동시에 돌면 CPU를 나눠 써서 **개별 분석이 ~5배 느려지고, 전체 처리량은 순차와 거의 같다.**
  동시 실행의 이득은 "모두 조금씩 진행되는" 체감이다. 처리량을 늘리려면 vCPU를 늘려야 한다
- 참고: dev에서 `내신마스터` 감지는 로컬 15s 대비 **1분 40초 이상**(0.5 vCPU + 동시 실행)

**비용 (ap-northeast-2 Fargate, 상시 가동 월 기준 대략치 — 2026-09-28 대화 추산)**

| 구성 | 월 | 비고 |
|---|---|---|
| 0.5 vCPU / 1GB (현재 dev) | ~$23 | 누수 수정 후 동시 5개 수용 |
| 메모리 +1GB (2GB) | +~$4 | |
| vCPU +0.5 (1 vCPU) | +~$18 | 처리량이 느는 유일한 축 |

**다중 태스크 주의** — "서버 시작 시 `PROCESSING` → `FAILED`"는 **태스크가 1개라는 전제**다.
운영에서 태스크를 2개 이상 띄우면, 새 태스크가 뜰 때 **다른 태스크가 지금 돌리고 있는 정상 작업까지 실패로 찍는다.**
다중 태스크로 가면 작업마다 소유 태스크·하트비트를 두는 식으로 바꿔야 한다. 세마포어도 태스크별이라
전역 동시 수는 `태스크 수 × 5`가 된다.

## 제약·함정

- **계약 #11 — 감지 정확도 > 성능.** 누수 수정은 결과를 바꾸면 안 된다. 완료 기준의 "완전히 동일"은 문항 수가
  아니라 **경계 전체 비교**다(수만 같고 y가 달라도 회귀)
- 누수 수정은 `detect_question_boundaries` 안이라 **모든 호출부(백그라운드 3곳 + 요청 경로 동기 폴백 + `pdf_service`)에
  적용**된다 — 호출부별로 따로 고치지 않는다
- **B16(문항 끝 그림 크롭)이 같은 루프에 `page.images + page.rects + page.curves + page.lines` 수집을 넣었다** —
  페이지를 닫는 지점은 이 수집까지 **끝난 뒤**여야 한다. 결과 동일성의 기준선도 B16이 들어간 코드로 잡는다
  (B16 전 코드로 잡으면 그림 하단 반영분이 "차이"로 보인다)
- **B16의 `pages_graphics`는 pdfplumber 객체 dict를 통째로 담는다**(B16 세션 확인, 2026-09-28) — 이미지 항목은
  원본 `stream` 참조까지 들고 있어, 페이지를 닫아도 **리스트가 쪽수만큼 객체를 붙잡아 누수가 남을 수 있다.**
  쓰는 값은 `x0`·`x1`·`top`·`bottom` 숫자뿐이니 그 넷만 복사해 담을 것. 메모리 재측정도 **B16이 들어간 코드로** 한다
  (이번 세션의 1,032MB → 154MB는 B16 이전 코드 실측)
- 감지 루프가 둘이다(`detect_question_boundaries`·`detect_question_boundaries_adaptive`) — 둘 다 페이지를 연다
- pdfplumber 페이지를 닫은 뒤 그 페이지 객체를 **루프 밖에서 다시 쓰는 코드가 있으면** 조용히 빈 결과가 날 수 있다 —
  결과 동일성 비교가 이걸 잡는다
- `BoundariesStatus`에 값이 하나 는다 — 이 상태를 **분기하는 모든 곳**(백엔드 통계·재감지 중복 가드·조회 경로의
  `PROCESSING` 체크, 프론트 `jobStatus.js`·목록 배지·파일 칩)을 함께 봐야 한다. 빠진 곳은 `QUEUED`를 "완료"나
  "알 수 없음"으로 조용히 취급한다
- `notification_service.emit_detection`의 docstring은 "호출부는 2곳뿐"이라고 못박고 있다 — 시작 시 전환이 세 번째
  호출부가 된다. 조회 경로(지연 감지)에는 여전히 붙이지 않는다는 그 docstring의 이유는 유지
- 세마포어는 **감지 + prewarm 전체**를 감싸야 한다 — 감지만 감싸면 prewarm 12스레드가 제한 밖에서 겹친다
- 측정 도구: `resource.getrusage(...).ru_maxrss`는 macOS에선 바이트, Linux에선 KB다. 프로세스 수명 최댓값이라
  단계별로 재려면 프로세스를 분리할 것(이번 실측이 그렇게 했다)
- **알려진 잔여 위험** — 요청 경로의 동기 감지 폴백과 PDF 생성은 제한 밖이다(범위 제외). 거기서 큰 파일이 겹치면
  여전히 메모리를 쓴다. 누수 수정으로 크게 줄지만 실측은 안 했다
