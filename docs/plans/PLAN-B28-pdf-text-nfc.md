# PLAN-B28 · 생성 PDF의 한글이 조용히 사라진다 — 그리기 직전 NFC 정규화

> 출처: 2026-10-05 dev 육안(사용자) + 같은 날 원인 규명 · 작성: 2026-10-05 · 상태: 🟡 진행
> (코드·테스트 완료 · `/review` 3회차 — 회차 2 의 (b) 는 감수 · **dev 육안 남음**: 백엔드 재배포 필요)

## 배경

dev에서 만든 문제집 PDF의 **출처 라벨에서 한글이 빠진 채** 나왔다.
문제집 이름 `2026 2학기 중3 내신마스터(1~3회)` 가 화면에선 정상인데 PDF에선 이렇게 보인다.

```
1번) 2026 2  ㄱ      3            (1~3  ). p4. 문항 4.
```

**빈 자리는 공백이 아니라 `\x00`(notdef) 다** — 글자가 안 그려진 게 아니라 **텍스트 레이어에서 사라졌다.**

원인은 셋이 겹친 것이고, 셋 다 실측으로 확인했다.

| # | 사실 | 확인 방법 |
|---|------|-----------|
| 1 | 이름이 **NFD(자모 분해)** 로 저장돼 있다 — `학` = `ᄒ`+`ᅡ`+`ᆨ` 3글자. **macOS 가 파일명을 NFD 로 돌려준다** | 아래 3의 일치 |
| 2 | `fitz.Font("korea")` 는 한글 폰트가 아니라 **`Droid Sans Fallback Regular`** 다. 완성형(`가`~`힣`)은 있지만 **한글 자모 블록(U+1100~)이 거의 없다** | `fitz.Font("korea").name` · 생성 PDF 의 `get_fonts()` (로컬·Docker·dev 산출물 모두 동일) |
| 3 | `TextWriter.append()` 는 글리프 없는 문자를 **에러 없이 notdef 로 바꾼다** | 같은 이름을 NFD 로 렌더한 결과가 dev 산출물과 **글자 단위로 완전 일치**. NFC 로 렌더하면 원문 그대로 |

**미리보기가 정상인 것은 결함이 아니라 증상이다** — 브라우저는 NFD 자모를 폰트 폴백으로 조합해 그린다.
그래서 **화면에서는 영원히 안 드러나고 PDF 에서만 드러난다.**

> **REQ-F17 탓이 아니다.** 옛 라벨 형식(`Q1 · 수학문제집 · p.3`)도 이름을 그렸고 폰트는 바뀐 적이 없다.
> 원래 있던 결함인데 **NFD 이름을 쓴 것이 이번이 처음**이라 지금 드러났다.

## 범위

**포함**
- `pdf_service.py` 가 **PDF 에 그리는 모든 사용자 문자열**을 그리기 직전에 NFC 로 정규화한다.
  그리는 통로를 **`_draw_text()` 하나**로 모으고 거기서 정규화한다 (`/review` 회차 1 결정) — 호출부는 둘이다
  - 출처 라벨 (`_build_grid_pdf`)
  - 각주 (`_apply_footnote`)
- 라벨의 **폭 계산(`text_length`)도 같은 문자열로** 맞춘다 — 2026-10-05 `/review` (c) 로 올라와 결정 표에 들어갔다

**제외**
- **저장 시점 정규화**(업로드 파일명 · `workbook_name` · `POST`/`PATCH`) — 2026-10-05 사용자 결정 "ㄱ 렌더 직전 NFC만".
  근본적이지만 **이미 저장된 데이터는 안 고쳐져** 결국 렌더 쪽 수정이 또 필요하다. 내일(10-06) 운영 오픈이라 손대는 경로를 늘리지 않는다.
  검색·정렬·중복 판정의 NFD/NFC 불일치는 **별도 REQ** 로 남긴다 → `docs/TODO.md`
- **기존 저장 데이터 마이그레이션** — 렌더 쪽을 고치면 기존 저장분도 즉시 정상 출력된다. 데이터를 건드릴 이유가 없다
- **폰트 교체**(진짜 한글 폰트 임베드) — 완성형은 이미 정상이라 이번 증상과 무관하고, 파일 크기·라이선스가 따라온다
- 프론트 `sourceLabel.js` 수정 — 브라우저는 NFD 를 정상 렌더하므로 고칠 것이 없다. **계약 #12(프론트↔백엔드 같은 문자열)를 깨지 않기 위해서도 건드리지 않는다**

## 제약·함정

- **이 계열은 에러를 내지 않는다.** 글리프가 없으면 `TextWriter` 가 notdef 로 **조용히** 치환한다 —
  로그도 예외도 없고, 테스트가 "문자열이 같은가"만 보면 **통과한다**. 검증은 **생성된 PDF 에서 텍스트를 추출해** 봐야 한다
  (계약 #18·#20·#29·#33 과 같은 "형식은 맞는데 조용히 틀리는" 계열)
- **단위 테스트가 자동으로 잡아 주지 않는다** — `build_source_label()` 은 문자열만 만들고 그리지 않는다.
  회귀를 막으려면 **실제로 렌더한 PDF 를 `get_text()` 로 되읽는** 케이스여야 한다
- **`fitz.Font("korea")` 라는 이름에 속지 말 것** — 한글 전용 폰트가 아니라 `Droid Sans Fallback Regular` 다.
  완성형은 있고 **자모 블록(U+1100~U+11FF)은 거의 없다**. 단 종성 `ᆨ`(U+11A8)처럼 **일부는 있어서**
  깨진 결과에 `ㄱ` 한 글자가 섞여 나온다 — "폰트가 한글을 아예 못 그린다"로 읽으면 오진한다
- **macOS 에서 올린 파일명은 NFD 다.** 같은 글자가 Windows/Linux 업로드에서는 NFC 로 온다 —
  **재현은 macOS 에서 올린 파일로만 된다.** 테스트 입력은 `unicodedata.normalize("NFD", …)` 로 **명시적으로** 만든다
- **소스 스캔으로는 "그리는 통로가 하나"를 증명할 수 없다 — 구문만 보기 때문이다.** B28-06 은 `fitz.TextWriter`
  **라고 쓰인** 생성지가 `_draw_text()` 안에만 있는지 본다. 그래서 **별칭**(`import fitz as _fitz` — 이 파일 72줄에
  이미 있다) · `from fitz import TextWriter as _TW` · `getattr(fitz, "TextWriter")` · `page.insert_htmlbox()` 같은
  **TextWriter 를 안 거치는 그리기**는 **못 본다**(전부 실측 PASS). 회차 0(창을 `fontsize` 로 끊기) → 회차 1(수신자
  모양 열거) → 회차 2(생성자 표기 열거)가 **같은 벽을 다른 각도로 친 것**이고, 네 번째 열거도 같다.
  2026-10-05 **감수하기로 결정**했다 — 레포 전체에서 `fitz.TextWriter(` 생성은 `_draw_text()` 안 한 자리뿐이라
  **현시점 노출이 0** 이기 때문이다. 끝내려면 런타임 가드나 타입 경계가 필요하고 그건 이번 범위가 아니다
- 프론트는 NFD 를 정상 렌더한다 — **미리보기로는 영원히 검증되지 않는다.** 육안 확인은 **생성된 PDF** 로 한다
