# PLAN-B29 · 문제집 메타 저장이 실패하면 만들어진 PDF 가 조용히 사라진다

> 출처: 2026-10-05 `/review F18` 회차 0 의 (c) · 작성: 2026-10-05 · 상태: 🟡 진행 (코드·테스트 완료 · `/review` 3회차 — **배포·확인 남음**)

## 배경

PDF 는 만들어졌는데 **사용자가 그 PDF 에 닿을 길이 없고, 어디에도 에러가 없는** 경로가 있다.

`extract.py` 의 백그라운드 작업은 생성에 성공하면 `status = DONE` 으로 올린 뒤
`_save_workbook_meta()` 로 문제집 행을 쓴다. 그 저장이 실패하면 **의도적으로 삼킨다** —

> `# 메타 저장 실패가 "PDF 생성 실패"로 둔갑하면 안 된다 — PDF는 이미 만들어졌다.`
> `# 상태는 DONE으로 두고 사유만 남긴다.`

**그 판단 자체는 옳다.** 문제는 그 뒤에 아무도 사용자에게 사실을 알리지 않는다는 것이다.

| 단계 | 실제 동작 |
|------|-----------|
| 상태 | `DONE` (성공) |
| 알림 | `emit_export` 가 **`job.status` 만 보고** severity 를 정한다 → **SUCCESS** |
| 결과 화면 | 목록이 **문제집 행** 기준이라 그 PDF 가 **안 뜬다** |
| 생성 화면 | **REQ-F18 이 다운로드를 걷어냈다** — 종전엔 `getStatus().download_url` 로 직접 받는 **유일한 탈출구**였다 |

즉 사용자는 **"완료!" 알림을 받고 결과 화면에 갔는데 아무것도 없는** 상태를 겪고,
우리는 `export_status.error` 문자열 하나 외에는 아무 신호도 못 받는다.

**F18 이 만든 결함이 아니다** — 구멍은 원래 있었고 F18 이 **우회로를 없애 드러냈다.**
2026-10-06 운영 오픈 직후 R2 가 한 번 흔들리면 바로 걸린다.

## 범위

**포함**
- `_save_workbook_meta()` 실패 시 **짧은 간격으로 3회 재시도**
- 재시도까지 실패하면 **완료 알림을 ERROR 로** 보낸다 — 사용자가 **모르고 지나가는 일**이 없게

**제외**
- **결과 화면이 job 기준으로도 목록을 보여주기** — 근본 해결이지만 백엔드 조회 API·프론트 목록까지
  범위가 커진다. 2026-10-05 사용자 결정(오픈 전날이라 건드릴 면이 넓다). 재시도+알림으로 **발생 확률과
  무지(無知)를 줄이는 쪽**을 먼저 한다
- **생성 화면 다운로드 되살리기** — REQ-F18 이 업무 분리를 위해 **의도적으로** 없앴다. 되살리면 그 결정이 조용히 뒤집힌다
- **`NotificationSeverity` 에 `WARNING` 추가** — enum 에 `SUCCESS`·`ERROR` 둘뿐이고 프론트 3곳이
  **이분법**(`severity === "error" ? … : …`)으로 그린다. 새 값을 넣으면 프론트가 전부 "성공"으로 떨어뜨린다(계약 #18·#20 계열의 조용한 오분류).
  **이번엔 기존 `ERROR` 를 쓴다**
- **상태를 `FAILED` 로 바꾸기** — 기각. PDF 는 실제로 만들어졌고, 상태를 뒤집으면 그 사실이 거짓이 된다

| 상태 | **`DONE` 유지** | PDF 는 실제로 만들어졌다. 기존 주석의 판단이 옳다 | `FAILED` 로 전환 — 사실이 아니게 된다 |

      **간격을 케이스로 박지 않았다** — 구현이 그 숫자에 묶이면 나중에 못 바꾼다

## 제약·함정

- ⚠️ **`emit_export` 는 `if workbook_name:` 바깥에 있어야 한다**(현재 그렇다) — 안쪽으로 옮기면
  **구 프론트로 만든 문제집은 영원히 알림이 안 온다.** 그 분기는 *메타 저장 주체*를 가르는 것이고(계약 #23)
  알림과는 목적이 다르다. severity 를 바꾸려고 이 구조를 건드리지 말 것
- ⚠️ **`emit_export` 의 severity 는 지금 `job.status` 하나로 갈린다.** 메타 저장 실패를 반영하려면
  **`status` 가 아닌 다른 신호**(예: `export_status.error` 유무)를 봐야 하는데, `error` 는
  생성 실패 경로에서도 채워진다 — **둘을 구분하지 못하면 "생성 실패"와 "메타 저장 실패"가 같은 알림이 된다**
- ⚠️ **상태를 `FAILED` 로 바꾸고 싶은 유혹을 참을 것** — PDF 는 만들어졌다. 바꾸면
  이력·재다운로드·통계가 전부 "실패한 작업"으로 읽는다
- **재시도는 백그라운드 작업 안에서 돈다** — 동시 실행 한도(REQ-B17, 5개)를 공유하므로 총 대기가 길면
  다른 생성 요청이 밀린다. 상한을 짧게 유지할 것
- ⚠️ **재시도는 멱등이어야 한다** — `workbook_id` 를 재시도마다 새로 만들면 **같은 키를 덮어쓰지 않고** 이력에 중복 행을 남긴다(계약 #23). B29-09 가 지킨다 — **대역을 `storage.save_workbook` 에 걸어 실제 저장 키를 본다.** `_save_workbook_meta` 를 통째로 갈아끼우면 "호출부가 무엇을 넘겼나"만 보게 돼 **함수가 그 인자를 쓰는지**는 아무도 안 본다(`/review` 회차 1 실측)
- ⚠️ **`message` 는 사용자에게 안 닿는다** — 스낵바·벨이 `title` 만 그린다. 문구로 무언가를 전하려면 **`title` 에** 넣을 것. B29-10 이 지킨다
- ⚠️ **재시도 간격을 `time.sleep` 으로 그냥 두면 테스트가 실제로 잔다** — 대역은 즉시 실패를 던지므로
  3회 재시도가 간격만큼 그대로 걸린다. 간격을 **주입 가능하게** 하거나 아주 짧게 둘 것
- `storage` 는 **임포트 시점에** 백엔드를 고른다(계약 #24) — 테스트는 `conftest.py` 격리 위에서만 돈다.
  재시도 테스트는 **`_save_workbook_meta` 를 직접 패치**해 실패를 만들고, 실제 R2 를 건드리지 않는다
