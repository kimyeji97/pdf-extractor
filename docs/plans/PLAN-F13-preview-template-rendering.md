# PLAN-F13 · 미리보기에 템플릿(표지·각주·워터마크) 반영

> 출처: 현재 세션 대화(2026-09-13 · 사용자 질문 "템플릿 적용하는 부분은 언제 작업해? 일부로 빠진건가?"에서 파생) · 작성: 2026-09-13 · 상태: ✅ 완료 (Phase 1~3 2026-09-13, 케이스 23/23 · `/testrun` 확인 · 육안 검증 완료 · 미결 0건 · PR #14 **main 머지 2026-09-13 `2fb290b`**)

## 배경

REQ-30으로 생성 화면에서 템플릿을 고를 수 있게 됐고, **생성 결과에는 실제로 반영된다**
(케이스 30-09가 `template_id` → 표지·각주·워터마크 세 id 전달을 단언한다). 그런데
**`WorkbookPreview`는 셋 중 아무것도 그리지 않는다** — 호출부에 `selections`·`layout`뿐이다.

그래서 **템플릿을 골라도 오른쪽 미리보기가 전혀 변하지 않는다.** 사용자에게는
"적용이 안 된 것"으로 보이고, 실제로 이 계획서는 사용자가 *"템플릿 적용하는 부분은 언제
작업해? 일부로 빠진건가?"*라고 물어서 시작됐다. **고른 것이 화면에 안 보이면 적용됐는지
알 방법이 없다** — 다운로드해 열기 전까지.

> REQ-30에서 이 작업을 `범위 — 제외`로 뺀 판단은 **"기술적으로 독립"만 본 것**이었다.
> 사용자 관점의 "선택이 결과에 어떻게 반영되는지 보이는가"를 계산에 안 넣었다.
> 제외 자체가 틀린 건 아니지만(완료 기준은 독립이 맞다) 후속 우선순위를 낮게 본 것은 틀렸다.

## 범위

**포함**
- `WorkbookPreview`가 **표지 페이지 · 각주 · 워터마크**를 그린다
- `GET /api/templates` 응답에 **표시용 정보**(자산 이름 · 각주 텍스트 · 표지/워터마크 이미지 URL)와
  **렌더 상수**(각주 글자 크기·여백·색, 워터마크 크기 비율·투명도)를 싣는다
- 생성 화면이 선택한 템플릿을 `WorkbookPreview`에 넘긴다
- **워터마크 알파 마스크 버그 수정**(REQ-29에서 들어온 결함, 2026-09-13 추가) — 아래 결정 참조

**제외**
- **렌더 상수 3개(워터마크 투명도 15% · 각주 8pt · 여백 12pt)의 스펙 확정** — 이번엔 현재
  백엔드 값을 그대로 쓰고, **미리보기로 눈으로 본 뒤** 정한다(2026-09-13 사용자 결정
  "한번 적용해보고 가자"). 아래 미결 질문 참조
- **픽셀 단위 일치** — 한글 폰트가 다르다(백엔드 `fitz.Font("korea")` ↔ 브라우저 시스템 폰트).
  아래 결정 "정확도의 한계" 참조
- **표지 이미지의 `contain` 재현 외 가공** — 백엔드가 `keep_proportion=True`로 A4에 넣는
  것만 재현한다. 크롭·필터 등은 범위 밖
- **`layout_spec.py` ↔ `workbookLayout.js` 상수 복제** — 아래 결정 "렌더 상수의 단일 출처"에서
  기각 (2026-09-13)

      완료 기준: 템플릿을 고르면 미리보기가 즉시 바뀐다 — 표지가 첫 페이지로 보이고, 나머지
      페이지 하단·좌측에 각주가, 중앙에 워터마크가 보인다. 표지 페이지에는 각주·워터마크가 없다.
      "없음"을 고르면 전부 사라진다.

## 제약·함정

- ⚠️ **PyMuPDF `insert_image`의 `mask`는 원본 알파를 곱하지 않고 통째로 대체한다.**
  균일 회색 마스크를 넘기면 **투명해야 할 배경까지 반투명**이 되고, 그 자리 RGB 가 보통
  (0,0,0) 이라 **연회색 사각 박스**로 보인다(실측: 흰 종이 255 위에 217). 계약 #29 가 지금
  `mask` 의 **형식**(bytes-like · `stream=` 과 짝)만 담고 있어 이 의미론이 빠져 있다 →
  **계약 #29 확장 후보**(`/checkpoint` 에서 제안).
- ⚠️ **미리보기와 PDF 가 갈리면 어느 쪽이 맞는지 먼저 가린다.** 이번 건은 **미리보기가 맞고
  PDF 가 틀렸다**(CSS `opacity` 는 알파를 곱한다). F13 이 만든 기준이 백엔드 결함을 찾아낸
  사례이고, 반대 방향(미리보기가 틀림)도 똑같이 가능하므로 자동으로 한쪽을 믿지 말 것.
- ⚠️ **표지 페이지에 각주·워터마크를 그리지 않는다** — 실제 PDF가 그렇다(위 결정). 미리보기가
  이걸 어기면 **실제와 다른데 눈에 잘 안 띈다.** 가장 놓치기 쉬운 지점이다.
- ⚠️ **`WorkbookPreview`의 `PAPER` 색은 여전히 토큰화하지 않는다**(계약 #14) — 새로 그리는
  각주 글자색도 마찬가지다. UI 색이 아니라 **생성될 PDF 지면을 재현한 값**이고, 다크 모드에서도
  종이는 희다. 계약 #20(tint)을 여기에 적용하려 하면 안 된다 — 두 규칙이 반대 방향이라
  헷갈리기 쉬운 자리다.
- ⚠️ **미리보기는 가상화돼 있다**(뷰포트 ±300px만 렌더, REQ-P02-07). 각주·워터마크는 페이지
  단위라 같은 조건에 얹으면 되지만, **표지 페이지를 목록 앞에 끼우면 페이지 인덱스가 1씩 밀린다** —
  스크롤·가상화가 인덱스를 쓰고 있는지 먼저 확인할 것.
- ⚠️ **렌더 상수를 프론트에 하드코딩하지 않는다.** 이번 결정의 핵심이다 — 서버 응답에서 읽는다.
  "어차피 15%인데" 하고 박아 넣으면 이 계획서의 이유가 통째로 사라지고, 계약 #12·#13·#14와
  같은 드리프트가 하나 더 생긴다.
- ⚠️ **`GET /api/templates`의 소비처가 둘이다**(생성 화면·관리 화면). 응답을 확장하면 관리
  화면의 `assetName()` 중복이 사라지는데, **그 정리를 같이 하지 않으면 두 경로가 공존**한다.
- 이미지 URL은 결정적이다(`/api/covers/{id}/image`·`/api/watermarks/{id}/image`) — 계약 #15와
  같은 결로, URL을 얻으려고 목록 API를 추가 호출하지 말 것.
