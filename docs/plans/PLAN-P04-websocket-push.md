# PLAN-P04 · 상시 폴링 → 서버 푸시 전환

> 출처: 2026-08-03 세션(REQ-F09 미결 검토에서 파생) + 2026-08-10 세션 · 작성: 2026-08-10 · 상태: 🟡 진행 (Phase 0 실측 완료 2026-08-18)

## 배경

**F09가 "모두의 알림"을 택하면서 폴링이 상시화됐다.** 내가 시작한 작업이 없어도 남이 시작한
게 끝날 수 있어 조건부 폴링이 성립하지 않는다 — 앱이 떠 있는 내내 5초(숨김 30초)마다
`GET /api/notifications`가 돈다.

**이 전환은 성능 개선이 아니라 조건 이행이다.** 2026-08-03에 사용자가 상시 폴링을 승인하며
붙인 조건이 *"차후 상시 폴링 하는 부분 모두 웹소켓으로 변경"*이었다. 그 약속의 이행분이다.

폴링으로는 못 푸는 것이 셋 있다:

- **비활성 탭 타이머 스로틀링** — 브라우저가 숨긴 탭의 타이머를 조인다(1초 → 5분 이상 숨기면
  intensive throttling). F09 Phase 6(브라우저 알림)의 지연이 여기서 나오는데, **타이머를 어떻게
  조절해도 없앨 수 없다.** 서버 푸시는 타이머가 아니라 메시지 구동이라 **제약 자체가 사라진다.**
- **다중 탭 배수** — 탭마다 독립 폴링이라 요청이 탭 수만큼 늘어난다(F09 미결에서 이관, 2026-08-10).
- **완료 인지 지연** — 활성 5초·숨김 30초는 폴링 주기의 하한이다.

> **전환 대상이 처음 예상보다 줄었다.** P04를 부여한 8-03 시점에는 폴링이 세 곳(알림 피드·
> 재감지·생성)이었지만, **F09 Phase 3이 화면 지역 폴링 2개를 이미 걷어냈다.** 지금 남은 상시
> 폴링은 **알림 피드 하나뿐**이다. 규모 추정("중~대")은 그 전에 매긴 값이다.

## 범위

**포함**

- 알림 피드의 상시 폴링을 **서버 푸시로 대체** (백엔드 커넥션 관리 신설 + 프론트 구독)
- 완료 시점의 서버 → 클라이언트 통지 (감지 완료·생성 완료·실패)

**제외**

- **알림의 사용자별 분리** — 인증이 없다(REQ-27). 커넥션이 생겨도 **소유자를 정의할 수 없어**
  "모두의 알림"은 그대로다. F09의 제외 항목을 그대로 승계한다.
- **F09가 만든 화면·데이터 구조 변경** — 벨·팝오버·스낵바·알림 저장소는 그대로 두고 **전달
  경로만** 바꾼다. 화면이 구독하는 대상(`useNotifications`)의 내부가 바뀌는 것이 이상적이다.
- **Phase 6(브라우저 알림) 구현** — F09 소관이다. P04는 그 지연 제약을 없앨 뿐이고,
  **P04가 끝나면 F09 Phase 6의 완료 기준(`___`초)을 다시 볼 수 있다**는 관계만 있다.

## 미결 질문

- [ ] **프로토콜: WebSocket인가 SSE인가.** F09 계획서는 둘을 "서버 푸시(SSE/WebSocket)"로 묶어
      제외했고 승인 조건의 문구는 "웹소켓"이었다. 알림은 **서버 → 클라이언트 단방향**이라 SSE로
      충분할 수 있다(재연결·`Last-Event-ID`가 프로토콜에 내장). 양방향이 필요해지는 시나리오가
      있는지 먼저 확인해야 한다.
      → **인프라는 중립이다(Phase 0, 2026-08-18)** — 둘 다 15분 통과·버퍼링 없음. 차이는 heartbeat
      부담뿐: WS는 uvicorn 기본 프로토콜 ping(20s)만으로 살고, SSE는 앱이 `: keepalive`를 직접
      보내야 한다. 그러니 선택은 재연결·폴백 설계 편의로 정한다(아래 폴백 미결과 한 묶음).
- [x] **Cloudflare Tunnel + ECS Fargate에서 장수명 커넥션이 되는가.** → **된다.** (Phase 0 실측
      2026-08-18, 아래 § Phase 0 결과) SSE·WS 모두 15분 무결점, 실시간(drift ~0.3s 상수).
      단 **오리진이 125초 동안 한 바이트도 안 보내면 edge가 끊는다** — heartbeat가 조건이다.
- [ ] **인스턴스가 늘면 어떻게 하나.** 지금은 ECS 태스크 1개라 프로세스 메모리에 커넥션을 들고
      있으면 되지만, 2개가 되는 순간 **다른 태스크에 붙은 클라이언트에게 알림이 안 간다.**
      지금 구조로 갈지, 그때 가서 브로드캐스트를 얹을지.
- [ ] **폴링을 완전히 걷을지, 폴백으로 남길지.** 커넥션이 끊긴 동안의 알림을 어떻게 복구할지와
      한 묶음이다 — F09의 `since` 기반 재동기를 재연결 직후에 한 번 쓰는 방식이 가능해 보이나
      정해진 바 없다.
- [ ] **완료 기준에 넣을 수치.** "지연이 줄었다"는 검증 불가능한 문장이다. 무엇을 몇 초 이내로
      잴지 정해야 한다. F09 Phase 6의 `___`초와 같은 자리이고, 같은 실측 하니스가 필요하다.
      → **절반은 답이 나왔다(Phase 0)**: 인프라 상수는 **idle 컷 125s → heartbeat 30s**(컷의 1/4),
      전달 지연은 **~0.3s**(HKG edge 왕복). 남은 건 "완료 → 화면 반영 N초"의 N — 폴링 5s/숨김 30s의
      하한을 대체하는 값이므로 **N ≤ 2s** 정도가 자연스럽지만 확정은 Phase 1 설계 때 한다.

## Phase 0 결과 — 인프라 실측 (2026-08-18)

**방법**: throwaway 브랜치 `feat/P04-phase0-probe`(커밋 `8b50a57`·`e8ac995`, 측정 후 삭제)에
`GET /api/_probe/sse`·`WS /api/_probe/ws`(heartbeat 간격·자동 종료를 쿼리로) + 측정 클라이언트
(도착 간격·drift = 클라 경과 − 서버 경과·종료 원인 JSONL). 이미지 `p04-probe` 태그로 dev에 배포
(태스크 정의 rev 3, `latest`는 안 건드림). 클라이언트는 이 머신(서울) → Cloudflare **HKG** edge.

| # | 모드 | heartbeat | 관측 | 결과 | 수치 |
|---|------|-----------|------|------|------|
| 1 | SSE | 15s | 15분 | ✅ 완주 | 60건, max_gap 15.3s, drift 0.29→0.29s (max 0.60) |
| 2 | WS | 15s + 60s마다 클라→서버 echo | 15분 | ✅ 완주·양방향 정상 | 74건, drift 0.33→0.31s |
| 3·3b | SSE | **없음** | 15분·5분 | ❌ **125.1s(서버 로그)·125.4s(클라)에 끊김** | 2회 재현 |
| 4 | WS | 앱 메시지 없음(uvicorn 20s 프로토콜 ping만) | 15분 | ✅ 완주 | 프로토콜 ping도 "데이터"로 친다 |
| 5 | SSE | 60s | 5분 | ✅ 완주 | drift 0.32→0.32s |
| 6 | SSE | 130s | 5분 | ❌ 첫 tick 전 **125.3s**에 끊김 | 컷은 "마지막 바이트 이후 125s" |

**결론**
- 경로는 장수명 커넥션을 **통과시킨다.** SSE·WS 모두 버퍼링 없음 — cloudflared의 GET-SSE 버퍼링
  보고([cloudflared#1449](https://github.com/cloudflare/cloudflared/issues/1449), Quick Tunnel)는
  named tunnel + 이 구성에서 **재현되지 않았다.**
- **idle 컷 = 125초.** Cloudflare 문서의 Proxy Read Timeout(오리진→edge 무전송 125s → 524)과
  정확히 일치한다([connection-limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)).
  60s heartbeat는 살고 130s는 죽는다. → **heartbeat 30s** 권장(컷의 1/4).
- **WS는 uvicorn 기본 `--ws-ping-interval 20`만으로 산다.** 이 값을 끄거나 125s 이상으로 올리면
  같은 컷에 걸린다 — 배포 CMD를 바꿀 때 기억할 것.
- **SSE는 앱 레벨 heartbeat가 필수**(`: keepalive` 코멘트 라인이면 충분).
- 백엔드 `TimeoutMiddleware`(30s)는 `BaseHTTPMiddleware`라 **응답 헤더까지만** 재고 스트림 본문은
  안 끊는다(로컬·dev 모두 확인). WS는 http scope가 아니라 아예 지나지 않는다.
- 우리 터널은 토큰 기반(원격 관리)·ingress `http://localhost:8000` 하나라 cloudflared 오리진
  파라미터는 전부 기본값(`keepAliveTimeout 1m30s`·`tcpKeepAlive 30s`)이다 — 바꾼 게 없다.

**측정 도구 결함 1건**: 3번 런에서 `http.client.IncompleteRead`(프록시가 청크 스트림 중간에 끊음)가
`OSError`가 아니라 summary 없이 죽었다. 서버 로그로 125.1s를 읽고, 분류를 고쳐 3b·6으로 재확인했다.
"끊김"은 EOF만이 아니다.

## 제약·함정

- **알림 쓰기 주체는 백엔드다**(계약 #22·#23, F09 § 결정). 푸시로 바꿔도 **"프론트가 완료를
  판정해 서버에 쓴다"로 돌아가면 안 된다** — B10에서 문제집이 사라진 구조가 그것이다.
- **기준선은 전송 방식과 무관하게 필요하다**(계약 #27). 재연결 직후 밀린 알림을 한꺼번에 받으면
  **앱을 열자마자 30일치 스낵바가 쏟아지던 것과 같은 사고**가 난다.
- **화면이 구독하는 표면을 바꾸지 않는다.** F09가 만든 `useNotifications`·`useJobCompletion`·
  `useNotificationRefresh` 뒤에서 전달 경로만 갈아끼우면 **화면 3곳(벨·목록·작업/편집)을
  다시 손대지 않아도 된다.** 표면까지 바꾸면 F09 검증 47건이 통째로 흔들린다.
- **`apiFetch`를 쓰지 않는다**(계약 #26). 폴링이 사라져도 초기 동기화·재연결 조회가 남는데,
  그 경로에 전역 딤이 켜지면 화면이 번쩍인다.
- **ECS 태스크가 1개라는 사실에 기대는 코드는 그 가정을 주석으로 남긴다.** 확장 시점에 조용히
  깨지는 종류이고, 위 미결(인스턴스 증가)이 답을 못 받은 채 구현되면 특히 그렇다.
- **오리진 무전송 125초면 edge가 스트림을 끊는다**(Phase 0). heartbeat를 "나중에" 붙이면 안 된다 —
  로컬(터널 없음)에서는 heartbeat 없이도 멀쩡해서 **로컬 테스트로는 안 잡힌다.** heartbeat 30s를
  구현의 일부로 넣고, WS라면 uvicorn `--ws-ping-interval`을 끄지 않는다.
