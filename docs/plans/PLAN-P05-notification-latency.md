# PLAN-P05 · 알림 전달 지연 — 발행 전 서버 작업 ~6s · 첫 진입 피드 GET 3.8s

> 출처: 2026-08-28 세션(TODO 2단계 후속) · 작성: 2026-08-28 · 상태: ✅ 완료 (Phase 1~3 2026-08-28 · 브랜치 `feat/P05-notification-latency` 푸시, main 미머지 · 미결 0건)

## 배경

P04가 **전달**을 폴링에서 SSE로 바꿔 전송 자체는 0.3~1.3s가 됐다. 그런데 사용자가 체감하는
"재감지 클릭 → 벨 뱃지"는 여전히 **9~12s**다(2026-08-27 브라우저 실측). 남은 시간은 전달이 아니라
**서버가 알림을 아직 발행하지 않은 구간**에 있다.

원인 두 가지가 코드에서 확인된다.

1. **발행 전 ~6s** — `_run_refresh_detection`은 감지 결과를 저장한 뒤 **썸네일 프리워밍**
   (전 페이지 + 문항별 크롭, R2 PUT 건당 ~270ms라 스레드풀로 병렬)을 돌리고, 알림 `emit_detection`은
   그 **뒤 `finally`**에서 나간다. 즉 사용자는 "감지가 끝났다"를 프리워밍이 다 끝나야 듣는다.
   프리워밍은 성능 최적화이고 실패해도 온디맨드로 폴백되는데, 그것이 **완료 통지를 붙잡고 있다.**
2. **첫 진입 피드 GET 3.79s** — `list_feed`는 키 이름만으로 정렬·필터해 파일 읽기를 최소화하도록
   잘 짜여 있지만, 마지막에 남은 **최대 50건을 순차로 한 건씩 `read_notification`** 한다.
   R2 왕복이 건당 수십~수백 ms라 여기서 시간이 쌓인다.

세 번째로 관찰된 **콜드 태스크 직후 `EventSource.onopen` ~31s**(warm은 0.2~0.8s, C09 실측)는
성격이 다르다 — 값이 heartbeat 주기와 정확히 겹쳐 앱 코드가 아니라 edge/터널 warm-up으로 보인다.

## 범위

**포함**
- 감지 완료 알림을 **프리워밍 앞으로** 옮긴다 (감지 결과 저장 직후 발행) — **재감지·최초 감지 두 경로 모두**
  (`browse._run_refresh_detection` · `upload._trigger_boundary_detection`, 2026-08-28 확인: 같은 순서)
- `list_feed`의 건별 `read_notification`을 **병렬**로 (prewarm이 이미 쓰는 `ThreadPoolExecutor` 패턴)
- 콜드 31s는 **조사·기록만** — 원인과 재현 조건을 계획서·PROGRESS에 남긴다
- dev 실측으로 전후 비교 (클릭→뱃지, 첫 진입 GET)

**제외**
- **콜드 31s의 해결** — 원인이 edge/터널 warm-up이면 앱 코드로 못 고친다. prod 환경(TODO 6단계)에서
  상시 가동이 되면 자연 해소될 수 있다 (2026-08-28 결정)
- **알림 인덱스 파일 도입** — 목록을 한 파일로 모아 GET 1회로 줄이는 안. 가장 빠르지만 쓰기 경합·정리
  로직이 새로 생긴다(현재는 키 이름만으로 정렬·30일 정리가 성립). 병렬 GET으로 충분한지 먼저 본다 (2026-08-28 기각)
- **초기 `limit` 축소(50 → 20 등)** — 근본 해결이 아니고 벨 팝오버 이력이 짧아진다 (2026-08-28 기각)
- **프리워밍 자체의 성능** — 병렬화는 이미 돼 있다(REQ-P03). 손대지 않는다
- 미리보기 URL 캐시 키 분리(R2 CORS) — TODO 2단계의 별건, 알림 경로가 아니다

## 제약·함정

- **알림은 정확히 1회다** — 지금 `emit_detection`은 `finally`에 있어 성공·실패 두 경로를 겸한다.
  발행을 앞으로 옮기면서 `finally`를 그대로 두면 **성공 시 2회** 발행된다. 알림이 2건이면 스낵바가 두 번
  뜨고 벨 뱃지도 2가 된다.
- **`emit`은 실패해도 호출부를 깨뜨리지 않는다**(현재 주석의 의도). 발행을 앞으로 옮겨도 이 성질을
  유지해야 한다 — 알림 실패가 "감지 실패"로 둔갑하면 안 된다.
- **저장 실패한 알림은 푸시하지 않는다** — `emit`이 이미 그렇게 갈라져 있다(재연결 재동기로 되찾을 수
  없으므로). 순서를 바꾸면서 이 분기를 흔들지 말 것.
- **`list_feed`의 필터 순서가 곧 비용이다** — 키 이름으로 다 거른 **뒤에** 남은 것만 읽는다(현재 주석).
  병렬화는 **마지막 읽기 단계에만** 적용한다. 앞단을 병렬로 만들 이유가 없다.
- **읽기 실패는 조용히 건너뛴다** — 현재 `read_notification`이 `None`이면 제외한다. 병렬로 바꿔도
  한 건의 예외가 전체를 깨뜨리면 안 된다(prewarm이 개별 실패를 건너뛰는 것과 같은 규칙).
- **테스트 스토리지 격리**(계약 #24) — 백엔드 케이스는 `conftest.py`의 세션 픽스처 아래에서 돈다.
  그 단언을 약화시키지 않는다.
- **콜드 31s 는 재현되지 않았다**(2026-08-28 Phase 3) — 같은 desired 0 → 1 직후 3회가 `onopen` 1004·269·344ms 였다.
  C09 때의 ~31s 와 조건이 같은데 값이 다르므로 **원인은 태스크 콜드가 아니라 edge 쪽 상태**로 보인다. 재현 조건 불명.
- **알림을 캐시 저장(경계·페이지·상태 R2 PUT)보다 앞으로 보내지 않는다** — 그 캐시가 없으면 알림을 보고 들어간 화면이
  읽을 것이 없다. 6.95s 중 3.2s 가 이 구간이고, 그래서 목표를 7s 로 정정했다(2026-08-28).
- **콜드 실측은 desired 0 → 1 직후에만 잡힌다** — warm 상태에서 재보면 0.2~0.8s가 나와 현상이 사라진다
  (C09에서 실제로 그랬다). 콜드 값을 재려면 서비스를 내렸다 올린 **첫 두 번**을 봐야 한다.
