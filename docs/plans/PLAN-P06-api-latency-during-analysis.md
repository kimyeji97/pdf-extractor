## 배경

문항 분석이 돌고 있으면 **분석과 무관한 화면까지 전반적으로 느려진다**(2026-09-29 사용자 체감: "API가 전반적으로 느린데").
그때 dev는 분석 9건이 몰려 CPU 100%가 이어졌고, 분석이 없을 때 `/api/stats`는 약 1s였다. 서비스 오픈(2026-10-06) 뒤에는
여러 사용자가 동시에 올리므로 분석 중인 상태가 평상시가 된다. **평시 `/api/stats` 약 1s도 이미 목표(1s 미만)에 걸린다** — 분석 중 지연만의 문제가 아니다.

오픈 전에 **운영 환경의 최소 사양**도 정해야 한다. 기준 사용량(2026-10-01 사용자 가정, 오픈 후 내려갈 수 있음): **사용자 10명 × (분석 5건 + 생성 5건) / 일** = 하루 분석 50건·생성 50건.

지금까지 확인된 사실(코드·기록):
- 감지는 업로드·재감지의 `BackgroundTasks`(동기 함수)로 **API와 같은 프로세스의 스레드**에서 돈다. 동시 한도 5개(B17 `analysis_slots`)
- PDF 생성은 이미 `ProcessPoolExecutor(2)`로 분리돼 있다 — P03-04에서 "CPU 작업이 메인 프로세스 GIL을 점유해 다른 요청을 지연"시켜서 옮겼다
- dev 백엔드는 Fargate 0.5 vCPU / 1GB
- 원인 추정 "분석이 같은 프로세스에서 CPU·GIL을 점유"는 **미검증**이다. `/api/jobs`·`/api/notifications`는 인증이 필요해 한 번도 재지 않았다

## 범위

**포함**
- dev에서 평시·분석 중 API 응답을 재현·측정하고 원인을 확인한다
- 원인이 확인되면 오픈 전에 조치한다
- 기준 사용량의 피크 부하에서 목표를 만족하는 **운영 최소 사양**(vCPU·메모리)을 dev에서 사양을 바꿔 가며 측정한다

**제외**
- **파일 업로드** — 목표(1s 미만)에서 예외. 파일 크기·네트워크에 묶인다(2026-10-01 사용자 결정)
- **SSE 알림 스트림**(`/api/notifications/stream`) — 목표에서 예외. 열려 있는 연결이라 응답 시간이 없다(2026-10-01 사용자 결정)
- **감지 결과를 바꾸는 최적화**(경로 건너뛰기·정밀도 낮추기) — 계약 #11 "문항 감지 정확도 > 성능", P03-06 기각(문항 15개 누락)과 같은 이유
- prod 환경 분리·CI/CD — TODO §6 인프라 항목(번호 없이 관리)

## 제약·함정

- **감지 정확도 > 성능**(계약 #11) — 조치가 감지 결과를 바꾸면 안 된다. 바꾸는 쪽을 택하면 기출 4종 + 테스트02로 main 대비 실측(계약 #35)
- **조회 경로는 감지를 돌리지 않는다**(계약 #34) — 지연을 줄이려고 감지를 요청 경로로 옮기거나 폴백을 되살리지 않는다
- **측정은 배경 요청이 섞이지 않게** — 목록·현황판은 알림 SSE가 올 때 배경 재조회한다(계약 #26·#27). 브라우저를 열어 둔 채 재면 측정에 그 요청이 섞인다
- **성능 실측 함정**(P05 기록): 표본 규모가 작으면 결론이 뒤집힌다 · 로그로 구간을 쪼개 본다 · 기본 UA는 Cloudflare에서 403이 날 수 있다
- **2 vCPU / 4GB 상시 비용은 약 $85/월(추정, 0.5 vCPU의 약 4배)** — dev는 쓸 때만 켠다(2026-10-01 사용자 결정)
- dev 비용 — 측정 동안만 `desired 1`(0.5 vCPU 기준 월 ~$23 수준, 사양을 올리면 비례해 늘어남), 끝나면 반드시 0
- **터널 vs 앱을 가르려면 앱을 직접 재야 한다** — 서버 로그엔 요청 시작 시각이 없어 터널 지연과 앱 대기가 구분되지 않는다. 태스크 공인 IP로
  직접 붙으려면 보안 그룹 8000번을 측정자 IP로 잠시 연다(자동 모드 분류기가 막아 사용자가 `!`로 실행, 끝나면 revoke). 태스크가 바뀌면 공인 IP도 바뀐다
- **사양 비교는 같은 데이터 양에서** — 이번 세 사양은 순서대로 재며 측정 job이 쌓여(사양마다 약 15건) 데이터 비례 API가 뒤 사양에서 더 느리게 나왔다.
  데이터 비례 API의 사양 효과는 이 측정으로 판단하지 말 것
- **피크 ②의 대기 5건은 B17 `QUEUED`** — 분석 10건을 올려도 동시에 도는 건 5건이다. 사양을 올려도 한도가 그대로면 대기 시간은 안 줄어든다(한도 조정은 조치 단계에서)
- **메모리 캐시는 "태스크 1 · 워커 1"을 전제한다** — 태스크·워커를 늘리면 다른 프로세스의 쓰기는 재적재 주기(60초)만큼 늦게 보인다. 늘릴 때 R2 인덱스 파일(기각안)을 다시 볼 것.
  새 저장 경로를 만들 때 `storage`의 save/delete 함수를 거치지 않고 R2에 직접 쓰면 캐시가 모른다
- **재적재가 조회를 막으면 p90이 깨진다** — 2026-10-02 첫 구현은 60초 재적재 동안 목록 조회도 기다리게 해, 60초마다 요청 하나가 R2 전체 읽기(~1s)를 기다렸다
  (알림 최대 1.75s · user 수동 상세 p90 1.18s 추정 원인). 재적재 중에는 기존 목록을 그대로 준다
- **시작 시 채우기는 쪽 목록 필드만 쓴다** — 읽어 둔 상태를 통째로 `put_status`하면 그 사이 감지·편집이 쓴 값을 덮는다. 쓰기 직전에 최신 상태를 다시 읽어 쪽 목록만 얹는다.
  채우는 동안에도 상세 조회는 옛 경로로 같은 답을 내므로 **기동을 막지 않게** 백그라운드로 돌린다
- **자식이 R2에 쓰는 것은 썸네일뿐** — 썸네일은 메모리 캐시 대상이 아니라 괜찮다. Linux는 fork라 부모의 boto3 클라이언트가 복사된다 — 연결 풀을 부모와 나누지 않게 자식 시작 시 클라이언트를 새로 만든다
- **감지 자식 프로세스는 R2 상태·캐시를 쓰지 않는다** — `s3_service` 메모리 캐시는 같은 프로세스의 저장만 안다. 자식은 감지 계산(`pdf_path → 경계 목록`)과 썸네일 렌더링·저장만 하고, 경계 목록은 부모에 돌려준다
- **분석 동시 한도 5 = 감지 프로세스 최대 5개 + 생성 프로세스 2개** — 프로세스마다 감지 모듈(pdfplumber·PyMuPDF)을 따로 올린다. 4GB에서 피크 ②를 다시 잰다(1GB OOM 이력, Phase 2)
- **테스트는 인라인 풀로** — 생성 풀의 `inline_extract_pool` 픽스처처럼 감지 풀도 테스트에서 인라인으로 바꿔야 감지 대역(`stub_detection` 등)이 먹는다. 자식 프로세스에는 monkeypatch가 안 건너간다
- **dev 태스크 정의는 rev 8 `:latest`(2026-10-01 상향, rev 4 정리됨)** — 측정용 이미지·리비전을 따로 만들면 반드시 정리한다(2026-09-28 프로브 rev 3 사고, CLAUDE.md 배포 상태)
