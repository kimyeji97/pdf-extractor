# PLAN-B19 · 분석 실패 파일 상세가 30초 504 — 조회 경로의 동기 감지 폴백

> 출처: 2026-09-28 세션(B17·B18 dev `c17f884` 확인 중 사용자 보고 + 스크린샷 2장, `docs/TODO.md` §7) +
> 2026-09-29 세션(AskUserQuestion 결정 3건) · 작성: 2026-09-29 · 상태: ✅ 완료 (Phase 1~3 2026-09-29 · PR #22 main 머지 `46c464e` · dev 배포 `f93e525` · 미결 3건 TODO §9로 이관)

## 배경

B17 Phase 2가 서버 시작 시 멈춘 분석을 FAILED로 바꾼다. 그래서 **경계 캐시가 없는 job이 목록에 정상적으로
나타나는 경로**가 새로 생겼다. dev에서 그렇게 FAILED가 된 `내신마스터`(212쪽, job `5065d74a…`) 상세에 들어가면
화면이 "Failed to fetch"가 된다. 백엔드 로그를 보면 `/api/jobs/{id}/questions`·`/pages/0/questions`가 30초 뒤
504(`TimeoutMiddleware`)로 끝났다. 브라우저에는 CORS 에러로 보였다.

원인은 조회 엔드포인트가 캐시가 없을 때 **요청 안에서 `detect_question_boundaries`를 동기로 돌리는** 폴백이다
(`browse.py`의 전체 문항·페이지 문항·문항 썸네일 3곳). 212쪽은 0.5 vCPU에서 30초를 넘긴다(B17 실측 1분 40초+).
타임아웃은 응답만 끊고 감지 스레드는 계속 돌기 때문에 **새로고침할 때마다 212쪽 감지가 하나씩 더 쌓인다.**
이 경로는 B17의 동시 5개 한도 밖이다(PLAN-B17 § 범위 제외 "요청 경로 안의 동기 감지"). 한도를 정할 당시에는
캐시 미스가 드문 경로였다. 게다가 폴백이 성공하면 상태를 **무조건 `DONE`으로 덮어쓴다.**

이 문제가 **B17 Phase 4(재감지 복구 확인)를 막고 있다.** 상세 화면에 들어가지 못해 재감지 버튼을 누를 수 없다.

같은 시각 관찰된 것이 둘 더 있다.
- **504에 CORS 헤더가 없었다.** 계약 #8(Timeout을 먼저 등록해 CORS가 바깥을 감싸게 함)은 코드상 지켜져 있는데도
  그랬다. 원인은 확인하지 못했다.
- **API 전반 지연**: `/api/stats` 9.06s · `/api/jobs` 5.64s · `/api/notifications` 3.04s. 폭주한 감지가
  0.5 vCPU를 점유한 시점과 겹친다는 추정만 있고 검증하지 않았다.

## 제약·함정

- **폴백이 `boundaries_status = DONE`을 쓰고 있다.** 감지를 걷어낼 때 이 대입도 함께 없어진다.
  조회는 상태를 읽기만 해야 한다. 조회가 상태를 바꾸면 FAILED·QUEUED가 조용히 DONE이 된다
- **`TimeoutMiddleware`는 응답만 끊고 작업은 끊지 않는다**(`asyncio.wait_for`). 동기 `def` 엔드포인트는
  스레드풀에서 끝까지 돈다. "타임아웃이 있으니 무거운 작업도 안전하다"는 가정이 이번 폭주의 뿌리다
- 기존 `PROCESSING` 가드(빈 결과 반환)와 새 캐시 미스 분기는 결과 모양이 같다. 프론트에서 둘을 구분해야 하는지는 미결 1을 볼 것
- 백엔드 테스트는 계약 #24(스토리지 격리)와 #30(`authed_client`)을 따른다
