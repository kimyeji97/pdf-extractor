## 1. 배경·목표

**요구**

- 대상: Minimal Dashboard Free 템플릿
- 목표: 템플릿 디자인을 **카피하는 것이 아니라 템플릿을 적용**한다
- 조건: **유저 플로우를 깨지 않는 선**
- 허용: UI/UX·디자인 변경
- 추가 예정 기능: 로그인/회원가입, 문제집 삭제, 표지 삭제, 라이트/다크 모드 전환, 문항 분석 완료 알림, 문제집 생성 완료 알림

**"카피가 아닌 적용"의 정의**

이 문서에서 "적용"은 **템플릿의 소스(테마 레이어 + 레이아웃 셸 + 공용 컴포넌트)를 우리 프로젝트에 이식해 그 위에서 우리 화면을 다시 짜는 것**을 뜻한다. 스크린샷을 보고 색·간격을 손으로 흉내 내는 것(카피)이 아니다.

구체적으로:

| | 카피 (하지 않음) | 적용 (이번 작업) |
|---|---|---|
| 색·타이포 | 눈으로 보고 hex 입력 | `theme/core/palette.ts`·`typography.ts`를 그대로 가져와 토큰으로 사용 |
| 카드·버튼 모양 | 컴포넌트마다 `sx`로 흉내 | 템플릿의 `components.tsx` 오버라이드를 테마에 등록 → 기본형이 바뀜 |
| 레이아웃 | 헤더/사이드바를 새로 그림 | 템플릿의 `layouts/core/*` 조립 구조를 셸로 채택 |
| 판단 기준 | "비슷해 보이는가" | "템플릿 토큰·컴포넌트를 쓰고 있는가" |

## 2. 사전 분석

### 2-1. 템플릿 실체

| 항목 | 내용 |
|------|------|
| 저장소 | `github.com/minimal-ui-kit/material-kit-react` (v3.0.0) |
| 라이선스 | **MIT** — 상업적 사용·수정·재배포 가능 |
| 스택 | React 19.1 / MUI 7.0 / Vite 6 / **TypeScript 5.8** / yarn |
| 구성 | `theme/`, `layouts/`, `components/`, `sections/`(데모 화면), `routes/`, `_mock/` |
| 무료판 범위 | 6개 데모 페이지(대시보드·유저·상품·블로그·로그인·404) |

> ⚠️ **MUI Store 페이지의 비교표는 실제 저장소와 다르다.** 스토어는 "TypeScript는 Pro 전용"이라 적었지만 무료 저장소 v3.0.0은 **전부 `.tsx`/`.ts`** 다. 반대로 스토어는 "라이트/다크 모드" 를 무료 기능처럼 적었지만, 실제 `theme/create-theme.ts`의 `colorSchemes`에는 **`light`만 정의돼 있다**(§2-4).

### 2-2. 우리 스택과의 호환성

| MUI | 7.3 | 7.0 | ✅ 동일 메이저 |

| 라우터 | `react-router` 7.9 | `react-router-dom` 7.4 | ⚠️ 패키지명 상이 — 템플릿의 `routes/*`는 안 가져오므로 영향 없음 |
| 아이콘 | `@iconify/react` 6 | `@iconify/react` 5 + 오프라인 아이콘 등록 | ⚠️ 템플릿 `register-icons.ts` 방식은 미채택, 현행 온디맨드 유지 |

**결론: 메이저 버전 충돌이 없다.** 이 작업의 난이도는 라이브러리 호환이 아니라 §3의 우리 쪽 스타일 계층 정리에 있다.

### 2-3. 핵심 발견 — 현재 코드도 이미 MUI 템플릿이다

`frontend/src`는 **Aurora 템플릿** 기반이다(테마 CSS 변수 접두사가 `aurora`, 모드 저장 키가 `aurora-mode`). 즉 이번 작업은 "무템플릿 → 템플릿"이 아니라 **템플릿 교체**다. 성격이 다르다.

현재 남아 있는 Aurora 자산:

| 영역 | 라인 수 | 성격 |
|------|--------|------|
| `theme/` | 3,063 | 팔레트·타이포·shadows + 컴포넌트 오버라이드 **41개** |
| `layouts/` | 1,849 | main-layout(AppBar·Sidenav·Footer) + **auth-layout(미사용)** |
| `providers/` | 210 | Settings·Theme·Breakpoints·SettingsPanel |
| `data/`, `lib/` | 2,928 | 템플릿 잔여 데이터·유틸 (상당수 미사용 추정) |
| `pages/`, `components/` | 6,913 | **우리 비즈니스 코드** |

`layouts/main-layout/common/AppbarActionItems.tsx`는 이미 **LanguageMenu · ThemeToggler · NotificationMenu · ProfileMenu** 4종을 붙여 두었고, `layouts/auth-layout/`도 존재한다(라우터에 미연결). 즉 **사용자가 원하는 "추가 예정 기능" 중 다크 토글·알림·로그인은 현재 템플릿에도 자리(슬롯)만 있는 상태**다. 다만 §2-4대로 알맹이는 없다.

### 2-4. 다크 모드 — 양쪽 무료판 모두 미구현

| | colorSchemes | 실제 동작 |
|---|---|---|
| 현재 Aurora | `light: {...}`, **`dark: false`** | `ThemeToggler`는 Pro 유도 스낵바(`ProSnackbar`)를 띄우는 껍데기 |
| Minimal Free | `light`만 정의 | 다크 팔레트 없음 |

**둘 다 다크 팔레트를 직접 작성해야 한다.** 그리고 진짜 비용은 팔레트가 아니라 하드코딩된 색이다(§3-2). 이 항목은 "템플릿 적용하면 따라오는 것"이 아니라 **별도 작업**으로 잡아야 한다.

### 2-5. 템플릿에서 무엇을 가져오고 무엇을 버리는가

**가져온다**

- `theme/` 전체 — `core/palette.ts`, `typography.ts`, `shadows.ts`, `custom-shadows.ts`, `components.tsx`, `create-theme.ts`, `theme-config.ts`, `theme-provider.tsx`
- `layouts/core/` — `layout-section.tsx`, `header-section.tsx`, `main-section.tsx`, `css-vars.ts` (조립식 레이아웃 셸)
- `layouts/dashboard/` — `layout.tsx`, `nav.tsx` (사이드바·헤더 구성)
- `layouts/components/` — `account-popover`, `notifications-popover`, `menu-button` (→ 추가 예정 기능의 UI 뼈대로 재사용)
- `components/` 중 `iconify`, `logo`, `scrollbar`, `label`, `svg-color`
- `sections/auth/sign-in-view.tsx` — 로그인 화면 뼈대로만

**버린다**

- `sections/` 데모 전부(overview·blog·product·user), `_mock/`, `components/chart`(+`apexcharts`), `components/color-utils`
- `routes/` — 우리 `routes/router.tsx`·`paths.ts` 유지
- `layouts/components/workspaces-popover`, `nav-upgrade`, `language-popover`(다국어 계획 없음)

### 2-6. 적용 방식 3안

| 안 | 방법 | 장점 | 단점 | 판정 |
|---|------|------|------|------|
| **A. 신규 프로젝트 베이스** | 템플릿을 클론해 새 프로젝트로 만들고 우리 코드 6,913줄을 이식 | 템플릿 구조가 100% 온전 | vite/tsconfig/alias/API 클라이언트 재구성, **P02·P03 작업물 유실 위험**, 중간 상태에서 앱이 안 돎 | ❌ |
| **B. 현 프로젝트에 이식 (in-place)** | 템플릿의 theme/layouts/공용컴포넌트를 우리 `src`에 넣고 Aurora 레이어를 걷어냄 | 라우팅·API·훅·성능 작업 전부 보존, **화면 단위로 점진 전환·검증 가능** | Aurora 잔재 제거를 별도로 챙겨야 함 | ✅ **권장** |
| C. 참고만 하고 현행 테마 수정 | Aurora 테마 값만 Minimal처럼 조정 | 가장 저비용 | **요구사항 위반**(= 디자인 카피) | ❌ |

**권장: B안.** 근거 — 우리 자산(라우팅, `api/client.js` 40+ 함수, `usePaginatedList` 등 훅, P02 가상화/memo, P03-03 무한스크롤)이 템플릿과 무관한 레이어에 있어 그대로 살릴 수 있고, 화면 단위로 갈아끼우며 매 단계 브라우저 검증이 가능하다. A안은 "다 갈아엎고 마지막에 켜보는" 구조라 회귀 지점을 특정할 수 없다.

## 4. 반드시 보존해야 할 계약 (회귀 방지 체크리스트)

리디자인 중 가장 깨지기 쉬운 지점들. 전부 **과거에 실제로 터졌던 것**이라 근거를 함께 남긴다.

| # | 계약 | 근거 | 깨지면 |
|---|------|------|--------|
| 1 | 스크롤 영역은 `flex:1; min-height:0` 높이 체인 | REQ-B04·B08 | 목록이 페이지 전체로 늘어나며 내부 스크롤 소실 |
| 2 | `PdfPreviewPanel` 소비처는 **flex 컬럼 부모**(`display:flex; flexDirection:column; minHeight:0`)를 제공 | REQ-B05·F07 | 뷰어 스크롤 불능 |
| 3 | `.pdf-page-wrapper { position: relative }` | 회귀 커밋 `c090d2a` | 오버레이가 상위로 쌓여 **수동 문항 좌표가 마지막 페이지에 고정** |
| 4 | 좌표 변환은 `pt = cssPx / scale` 단일 공식 | REQ-F07 | 문항 영역 어긋남 |
| 5 | 살아있는 클래스는 CSS 정리 시 동반 삭제 금지 (사용처 전수 확인) | 회귀 커밋 `c090d2a`(데드코드 정리 중 `qlist-*` 실수 삭제) | 문항 선택 스타일 소실 |
| 6 | 뷰어/미리보기 **IntersectionObserver 가상화** | REQ-P02-01·07 | 206페이지 문서에서 전 페이지 렌더 |
| 7 | 리스트 항목 `React.memo` 비교자(편집 상태 포함) | REQ-P02-04 | 타이핑마다 전체 리렌더 |
| 8 | 무한 스크롤 센티널 + 서버 검색 | REQ-P03-03 | 목록 페이징 소실 |
| 9 | `scrollToPage`는 대상+다음 페이지만 강제 렌더 | REQ-P02-01 버그 수정 | 페이지 점프가 한 페이지 짧게 안착 |

> 특히 #3·#5는 **"안 쓰는 CSS인 줄 알고 지웠다가" 터진 사례**다. `App.css` 1,061줄을 정리할 때 클래스 단위로 사용처를 확인하고 지운다.

### Phase 1 결과 (`bcc2e35`)

- **테마는 템플릿 원본 그대로** 이식(palette·typography·shadows·custom-shadows·components + create-theme·theme-config·theme-provider). 레이아웃은 core 조립 primitives를 그대로 쓰고 dashboard layout·nav만 우리 4개 라우트에 맞춰 새로 작성.
- `minimal-shared` 설치 — 헬퍼(varAlpha/setFont/pxToRem/mergeClasses)를 재구현하지 않았다. 폰트는 `@fontsource`로 자체 호스팅해 **index.html의 Google Fonts 링크 제거**(외부 CDN 의존 없음).
- **높이 체인이 핵심 적응 지점**: 템플릿은 body가 스크롤되는 문서형 전제. root(100dvh) → sidebarContainer → main 전 구간에 `flex:1`/`minHeight:0`/`overflow:hidden`을 걸어 바깥이 절대 스크롤되지 않게 했다.
- 헤더 72→56px, 본문 패딩 0, 헤더에 현재 화면 이름 표기(빈 헤더 방지). 우측은 D08/F09/REQ-27 자리로 비워 둠.
- MUI 7.3에서 `shape.borderRadius` 타입이 `number | string`으로 넓어져 `Number()`로 감쌈(템플릿은 7.0 기준).
- **123파일 삭제 / 24파일 추가, 메인 번들 955KB → 495KB.**

> **부수 발견**: 도달성 분석 중 우리 코드의 죽은 파일을 찾았다 — `QuestionPicker`(624줄)·`SelectionBasket`(366줄)·`StatusPoller`·`QuestionInput`·`NavMenu`. §3-1에서 Phase 3 마이그레이션 대상으로 잡아 둔 파일들이라 **남은 작업량이 ~1,100줄 줄었다**.

### Phase 2 결과 (`d457ede`)

- 인라인 `const styles = {}` **0개**(FileListPanel을 sx로 재작성).
- 하드코딩 hex **JSX 48개 → 0개**.

## 4-2. 2안 적용 범위 확정 (2026-07-29)

Phase 3-5까지 끝낸 뒤 **결정 기록과 실제 구현이 갈라져 있다는 것이 발견됐다.** §8 #8은 "2안 채택"인데
지어진 화면 4개 중 3개가 아티팩트 1안이었다 — 작업 화면 2개는 맞붙은 패널 그대로였고, 목록은 조건 ①로
테이블 전환을 안 했으며, 셸은 밝은 사이드바만 2안이었다. 즉 아티팩트가 하단에서 **"권장"한 하이브리드**로
지어져 있었는데 그 이탈이 어디에도 기록되지 않았다.

사용자 결정: **기록이 아니라 구현을 2안에 맞춘다.** 화면별 적용 범위는 아래로 고정한다.

| 아티팩트 비교 대상 | 2안 적용 | 비고 |
|---|:---:|---|
| 앱 셸 | ✅ | 워크스페이스 선택기 · 헤더 검색 · 요약 통계 카드 추가 (밝은 사이드바는 Phase 1에서 완료) |
| 분석 목록 | ❌ **의도적 예외** | 2안은 "테이블 + 툴바"인데 **조건 ①이 테이블 전환을 금지**하고 B안 책 카드가 확정안이다. 2안의 공통 요소(페이지 헤더·브레드크럼)만 받는다 |

### Phase 3. 화면별 재구성 — **2안(구조 변경) 채택**

2026-07-25 결정: **2안(템플릿에 맞는 UI 구조로 변경)**. 단 아래 두 조건을 건다.

> **조건 ①** 문제집/파일 **목록을 보여주는 곳은 카드 그리드를 유지**한다(테이블로 바꾸지 않는다). 대신 카드를 **"책" 형태로 개선**한다.
> **조건 ②** 문제집 편집에서 **여러 파일의 문항을 섞어 선택**할 수 있어야 한다.

유저 플로우(업로드 → 감지 → 선택 → 레이아웃 → 생성)의 **순서 자체는 바꾸지 않는다.** 바뀌는 것은 화면 내부 배치와 컴포넌트 어휘다.

| 3-1 | 분석 목록 (`pages/analysis/index.jsx`) | **카드 그리드 유지(조건 ①)** + 페이지 헤더·브레드크럼·헤더 검색 도입. 카드는 책 형태로 재디자인(§5-1) |

#### 5-1. 목록 카드 — 책 디자인 (조건 ①) · **B안 확정**

카드 그리드를 유지하되 "파일 카드"가 아니라 **책(문제집)** 으로 읽히게 한다. 지금 카드는 1페이지 썸네일 + 이름 + 문항 수 칩 구성이다.

**시안 3종(A 책등만 / B 책등+두께 / C 책등+띠지) 중 B안 확정** (2026-07-25).

| 요소 | 사양 |
|------|------|
| 표지 | 세로 장방형(현재는 정사각형에 가까움). 내용은 1페이지 썸네일 |
| 책등 | 좌측 세로 띠 + 안쪽 그림자(gradient)로 두께감 |
| 책등 색 | 문제집 **유형**(`workbook_types[0]`)에 매핑. **유형 미지정은 회색** — 실제 데이터에 미지정이 많으면 이름 해시 자동 배정으로 전환 검토 |
| **두께(페이지 스택)** | 우측에 겹친 종이 층. **문항 수 구간에 연동**해 층 수를 2~4단계로 (두께가 정보가 되게) |
| 감지 전/실패 | 층 1단(가장 얇게) + 배지로 상태 표시 |
| 상태 배지 | `boundaries_status`를 표지 우상단 배지로 (완료/감지 중/실패) |
| 정보 영역 | 표지 아래에 이름 · `N문항 · Mp` · 유형 칩 |

**구현 주의**

- **카드 폭은 층 수와 무관하게 고정**한다. 층이 폭을 밀면 래핑 그리드 정렬이 문항 수에 따라 흔들린다. 층은 카드 내부 우측 여백 안에서 그린다.
- 썸네일 URL 조립 방식은 **P02-02 최적화를 그대로 유지**한다(목록 API 추가 호출 금지).
- 두께 연동이 과하다고 판단되면 층 수를 상수로 고정하는 것만으로 되돌릴 수 있게 분기 지점을 한 곳에 둔다.

#### 5-2. 문제집 편집 — 멀티 파일 선택 (조건 ②)

**사전 확인 결과: 기능은 이미 동작한다. 문제는 UI에서 그렇게 보이지 않는 것이다.**

| 확인 항목 | 현재 상태 |
|---|---|
| 파일 전환 시 선택 유지 | ✅ `handleJobSelect`는 `jobId`만 바꾸고 `basket`을 비우지 않음 |
| 항목별 출처 보관 | ✅ `toggleSelection`이 항목마다 `jobId`·`workbookName` 저장 |
| 키 충돌 | ✅ `question_id`가 `{job_id}:{page}:{num}` 복합키(ADR-0002) |
| 백엔드 | ✅ `POST /api/extract-v2`가 멀티소스 전제 |
| **③ 순서 편집에서 출처 표시** | ❌ **`SelectionBasket`이 `pageNum`만 표시하고 `workbookName`을 쓰지 않음** |
| 파일별 선택 개수 | ❌ 없음 |
| 선택 항목이 있는 파일 표시 | ❌ ① 파일 목록에 표시 없음 |

즉 조건 ②는 **신규 기능이 아니라 가시성 작업**이다. 필요한 것:

1. `SelectionBasket` 항목에 **출처 문제집 이름** 노출 (데이터는 이미 `item.workbookName`에 있음)
2. ① 파일 목록 카드에 **"이 파일에서 N개 선택됨"** 배지
3. 상단에 `N개 선택 · M개 파일` 요약
4. (선택) 바스켓을 출처별로 묶어 보기 토글

> 라벨 문자열은 REQ-C07에서 `sel.label` 단일 출처로 통일했으므로, 출처 표시를 추가할 때 **미리보기·PDF 라벨과 중복되지 않게** 화면 표시용으로만 쓴다.

### 8-1. 한글 폰트 처리 (결정 2의 후속)

DM Sans는 라틴 전용이라 한글은 폴백 폰트로 렌더된다. 방치하면 **관리자 PC마다 한글 모양이 달라진다**(현재도 한글 웹폰트 미지정 상태라 같은 문제가 있다).

- 웹폰트를 새로 추가하지 않고, `fontFamily`에 한글 시스템 폰트를 **순서대로 명시**한다:
  `'DM Sans Variable', 'Apple SD Gothic Neo', 'Malgun Gothic', 'Noto Sans KR', sans-serif`
- 라틴·숫자는 DM Sans, 한글은 OS 기본 고딕으로 떨어져 템플릿 인상은 유지된다.
- 한글 모양을 완전히 통일하려면 Pretendard 등 웹폰트 도입이 필요한데, 이는 별건으로 남긴다(로딩 비용 발생).

## 10. 결론

- 템플릿은 **MIT + 스택 호환**이라 도입 자체에 걸림돌은 없다.
- 실제 작업은 "템플릿 붙이기"가 아니라 **Aurora 템플릿 → Minimal 템플릿 교체 + 우리 화면 5,098줄 재구성 + 스타일 계층 3중 혼재 정리**다.
- 가장 큰 리스크는 디자인이 아니라 **§4의 9개 계약**이다. 전부 과거에 실제로 터졌던 지점이고, 특히 PDF 뷰어 좌표·높이 체인은 육안으로 즉시 드러나지 않는다.
- 다크 모드는 템플릿을 붙이면 따라오는 기능이 **아니다**(양쪽 무료판 모두 미구현 + 하드코딩 286개). Phase 2 이후 별도 작업으로 잡는다.
- 로그인/회원가입은 성격이 달라 **REQ-27로 분리**를 권한다.
